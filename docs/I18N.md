# Internationalization Readiness

Toolhub Evolved is not translated yet. The production source locale is English;
`public_html/i18n/` contains `en.json` (the source catalog), `qqq.json` (message
documentation for translators), and a generated `locales.js` listing the shipped
catalogs. `AVAILABLE_LOCALES` also includes the QA-only `en-x-pseudo` locale,
which generates pseudolocalized English at runtime to expose hardcoded strings
and layout issues.

Messages use the **banana format**, the same one upstream Toolhub and
translatewiki use: positional `$1` parameters plus the `{{PLURAL:…}}` and
`{{bidi:…}}` magic words. That is why a translatewiki message group needs no
bespoke configuration, and why `banana-checker` can validate parameter parity
between `en.json` and every translation.

The goal for current feature work is source-message readiness: every new UI
surface should be easy to hand to translatewiki later, without a broad rewrite.
Actual translatewiki export/import and shipped non-English catalogs are tracked
separately in #118.

## Current Contract

- UI chrome uses `t("stable.key", "English source", ...params)`.
- `tools/i18n-extract.mjs` extracts those calls into `public_html/i18n/en.json`,
  refreshes `qqq.json` while preserving human-written guidance, and regenerates
  `i18n/locales.js`.
- `npm run i18n:extract` rewrites all three.
- `npm run i18n:check` fails when generated files are stale, any message lacks
  qqq documentation, a shipped locale is incomplete, or a translation changes
  the source message's positional parameters.
- `npm run lint:banana` runs `banana-checker` — the check translatewiki itself
  applies. Keys here are `namespace.camelCase`, so it runs with
  `--requireLowerCase=false`; nothing else is relaxed.
- Non-English catalogs are not shipped yet. A locale with no catalog 404s from
  `/i18n/<locale>.json` and falls back to the English source strings.
- `en-x-pseudo` is selectable from the language picker but does not fetch a
  catalog. It accents, brackets, and expands source messages at runtime.

### Message documentation (`qqq.json`)

translatewiki expects every message documented. The catalog is held at zero
documentation debt: `i18n:extract` generates baseline context from each stable
key and an explicit `Parameters:` entry for every `$n`, while preserving more
specific human-written guidance. `i18n:check` rejects stale output and any
legacy `TODO` stub. Improve generated wording whenever a translator would need
more product context; regeneration will keep that human text intact.

### Shipped locale quality

Every non-English JSON file in `public_html/i18n/` is a shipped locale. The
extractor requires it to contain exactly the English source key set, rejects
empty translations, and checks `$1..$n` parity per message. Keep an incomplete
translatewiki export outside that directory until it is ready to ship.

Human review is recorded per locale/key pair in `.i18n-review.json`, including
the reviewer and ISO date. `i18n:check` verifies that each record points to a
real shipped translation; the empty initial manifest accurately records that no
non-English catalog has been reviewed or shipped yet.

Runtime lookups maintain content-free counters for catalog hits, English
fallbacks, and missing keys. They are included under `translations` in page
diagnostics and issue reports, making fallback rate visible without collecting
the translated strings or user data.

## Source Message Rules

Use stable dot-separated keys:

```js
t("apiExplorer.runRequest", "Run request");
```

Use whole messages with positional parameters:

```js
t("apiExplorer.requestComplete", "GET $1 returned $2 in $3 ms.", path, status, duration);
```

`$1` is the first argument after the English source, and a translation may put
them in any order. Braces are ordinary text in banana, so a message may contain
a literal `{name}` — an API path template like `GET /api/tools/{name}/` is fine.
The extractor only rejects `{name}` in a message that is _also_ passed
arguments, which is what a call site left over from the old syntax looks like.

### Plurals

Never select a plural form in JavaScript, and never build one from two messages.
English needs two forms, but Russian and Polish need four, Welsh five, and Arabic
six — a `one`/`other` pair gives translators no key to put the others in:

```js
// Bad: only ever two forms, and the verb cannot agree with the noun.
countLabel(n, t("lists.toolOne", "tool"), t("lists.toolOther", "tools"));

// Good: one message owns the number, the noun, and any agreement.
t("lists.toolCount", "$1 {{PLURAL:$2|tool|tools}}", fmt(n), n);
```

Pass the formatted number for display and the raw number for selection —
`{{PLURAL:}}` needs a real number, and `fmt()` localizes digit grouping. Keying
the plural on a different parameter than the one displayed is normal banana; it
is what upstream Toolhub's `search-result-summary` does.

An explicit `N=` form wins for that exact count:

```js
t("search.resultCount", "{{PLURAL:$1|0=No results|$1 result|$1 results}}", n);
```

### Direction isolation

Wrap an interpolated value that may be RTL in `{{bidi:$n}}` so its direction
cannot leak into the surrounding sentence. This is for values _inside_ a message;
markup-level `dir="auto"` on API data stays as it is.

Do not concatenate translated fragments:

```js
// Bad: translators cannot reorder this sentence.
t("home.ctaBodyBefore", "Add a ") + "toolinfo.json" + t("home.ctaBodyAfter", " to your repository.");
```

Prefer a single source message and keep markup outside it where practical:

```js
tWithElements("home.ctaBody", "Add $1 to your repository so other Wikimedians can find it.", {
	html: "<code>toolinfo.json</code>"
});
```

`tWithElements()` takes the same positional parameters as `t()`. A parameter
wrapped as `{ html }` is inserted as trusted markup; every other parameter, and
the translated text itself, is escaped. Wrap only caller-owned markup from
trusted atoms or static snippets — never API data, and never a translation.

The extractor intentionally rejects source messages with:

- non-literal keys or English fallbacks
- keys outside the existing dot-separated ASCII convention
- prose-fragment keys such as `...BodyBefore` or `...IntroAfter`
- HTML inside compact UI messages
- magic words beyond `{{PLURAL:}}` and `{{bidi:}}`, which would render verbatim
- gaps in the `$1..$n` sequence, or a count that disagrees with the call site
- a `{name}` placeholder in a message that is passed arguments

## Review Checklist

When reviewing new or changed frontend UI copy, check that:

- user-visible chrome, labels, placeholders, status text, and ARIA labels are
  backed by `t()` or `tWithElements()`
- source messages are whole sentences where word order may vary by language
- parameters are positional (`$1`, `$2`), and every one is passed at the call site
- **any count uses `{{PLURAL:}}` inside one message** — no `n === 1` ternary, no
  separate singular/plural keys, no sentence assembled from a count plus a noun
- **new or renamed keys arrive documented in `qqq.json`**, with a `Parameters:`
  block naming what each `$n` is
- inline markup is supplied through `tWithElements()` as `{ html }`, not embedded
  in the source message
- live Toolhub API values stay data and keep `dir="auto"` / `lang` handling

## Current Exceptions

The static HTML shell in `public_html/index.html` still carries English as a
no-JS and first-paint fallback. Active app chrome is localized by
`localizeShell()` in `public_html/main.js`, and those source messages are present
in `public_html/i18n/en.json`.

Styleguide sample data, code snippets, example URLs, fixture tool names, and
fixed brand/version labels remain data/specimens rather than UI messages.
Styleguide headings, labels, ARIA text, captions, and explanatory demo copy are
source-backed like the rest of the app.

## UI Copy Versus Data

Do not translate live Toolhub API data as if it were UI chrome. Tool names,
descriptions, authors, comments, and catalog metadata are data. Keep using
`dir="auto"` and `lang` metadata where the API exposes language information.

For localized Toolhub data fields, use the helpers in `lib/core/i18n.js`
(`localizedField()` / `pickLocalized()`) so the app prefers the active locale
once real multilingual fields are available.

## Pseudolocalization

Use the language picker and select `Pseudolocalization` (`en-x-pseudo`) during
local QA. Chrome strings should render bracketed, accented, and expanded. Plain
English that remains in app chrome usually means a new surface skipped `t()`,
`tData()`, or `tWithElements()`.

Pseudolocalization intentionally leaves positional parameters such as `$1` and
caller-provided values unchanged. Live Toolhub data is not translated or accented;
it should keep its own `dir="auto"` and `lang` metadata.

The Playwright pseudolocale smoke test checks the core shell, search route, and
language menu for transformed chrome and horizontal overflow.

## Font Coverage

The design system still uses native Wikimedia/Codex-style system fonts and makes
no third-party font requests. Target-script fallback decisions live in
`public_html/styles/tokens.css` and the matching first-paint token copy in
`public_html/index.html`.

Current fallbacks cover the major QA scripts without loading web fonts:

- Arabic and Hebrew: system UI faces first, then `Geeza Pro`, `Arial Hebrew`,
  and Noto script fallbacks where installed.
- Indic scripts: `Nirmala UI`, `Kohinoor Devanagari`, and Noto Indic fallbacks.
- CJK: `PingFang SC`, `Hiragino Sans`, `Apple SD Gothic Neo`, Microsoft CJK UI
  fonts, and Noto CJK fallbacks.

Add locale-specific CSS only after visual QA shows a script-specific issue that
the shared token stack cannot cover.

## Static Prose

Long prose pages now expose English source messages through `t()` and
`tWithElements()`, with inline links/code passed as placeholders. This makes the
current surfaces translatewiki-ready, but the preferred long-term architecture is
still per-locale fragments with markup sanitization rather than very large JS
message calls. That work is tracked in #88.

Until shipped non-English catalogs are wired, keep static prose changes
deliberate and do not claim the pages are translated.

## What Not To Claim

Passing `npm run i18n:extract` means the English source catalog is current. It
does not mean the UI is translated. Use “translation-ready English source
messages” unless real non-English catalogs are present and selectable.
