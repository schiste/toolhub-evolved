# Technical Release Notes

- Adds a durable digest domain over captured official tool-creation events, immutable edition/tool snapshots, publication state, channel subscriptions, and a restart-safe delivery outbox. UTC day, ISO-week, and calendar-month boundaries are deterministic, generation is idempotent, missed closed periods recover automatically, empty periods are suppressed, and idempotent MariaDB migration widens complete rendered bodies to `MEDIUMTEXT`. Public catalog reads now resolve locally through `/v1/catalog/*`; complete Toolhub snapshots stage by generation and publish in one transaction, failed imports preserve the prior generation, the obsolete request-time HTTP client and revalidation worker are removed, and scheduled workers are the only anonymous Toolhub network readers. Canonical ingestion derives compact card JSON and indexed UTC modification timestamps, background jobs atomically publish global facet aggregates, filtered facets use a covering index and independent endpoint, redundant canonical revalidation is removed, and card rendering no longer waits for facet or summary enrichment. Projection version 4 lifts Toolhub `tasks` and `audiences` annotations without treating API-owned annotations as top-level fields; one shared facet vocabulary preserves legacy `technology` compatibility while exposing canonical `detected_technology`, `declared_technology`, and `ui_language` names across REST and MCP. MCP search uses the atomic local replica, GET `/mcp` returns a structured 405 pointing to a lazy-loaded in-app guide with client-specific configurations, and every new message includes translator documentation. Release notes remain collapsed when no deployment record exists.
- Integrates LiftWing's public OpenAI-compatible `llm-qwen36-27b` chat-completions endpoint with strict Wikimedia host/path/model validation, contact-bearing user-agent headers, bounded timeouts and citation-only payloads, period-wide candidate sampling for busy weekly and monthly editions, Qwen reasoning-tag removal, schema validation, unique supplied-title normalization to canonical tool ids, exact full-field or whitespace-normalized verbatim excerpt evidence checks, and an audited deterministic fallback with sanitized failure details. Daily requests and responses cover every supplied tool exactly once; weekly and monthly responses select exactly `min(total, 5)` tools; omissions, duplicates, ambiguous or invented identifiers, paraphrases, and trivial fragments remain fail-closed. A database-free live preflight exercises production facts through inference, validation, and rendering before deployment.
- Publishes canonical edition pages and the archive tree on Meta through a bearer-authenticated Wikimedia Action API client that restricts destinations, verifies the configured service-account identity, bounds responses, refreshes CSRF tokens, and classifies permanent recipient failures. The same client appends talk-page sections and calls `emailuser` without adding SMTP infrastructure. Configuration-sourced outbound header values are now validated next to the configuration that supplies them rather than inside `requests`: `proxy/backend/http_headers.py` folds interior whitespace runs in descriptive values, because a Toolforge envvar wrapped across lines unambiguously means its single-line form, and refuses whitespace or control characters in credentials, because folding a token would transmit something other than what was configured. Error messages name the variable and never quote its value, which is what makes them safe to return; `WikimediaClient` construction failure is a 500 naming the envvar rather than a 502 that would misdirect an operator upstream, and `LIFTWING_USER_AGENT` is validated inside `generate_editorial()`'s fallback guard so a malformed value degrades to deterministic copy with a recorded diagnostic instead of stopping publication. `WikimediaClient` additionally redacts its access token from transport-exception text, since `requests.InvalidHeader` quotes the offending header value verbatim and that string reaches both the API response body and the stored per-subscription `last_error`. All three 502 branches of `POST /v1/digests/subscriptions/` now log; the module previously imported no logger. The service-account assertion in `csrf_token()` compares MediaWiki spellings rather than raw strings: `WIKIMEDIA_ACCOUNT_NAME=NellieBly_Bot` and the Action API's `NellieBly Bot` name one account, and raw equality made the writer fail to recognize itself and route every write into the permanent `unexpected-account` branch. `canonical_username()` is split out of `normalized_username()` for this, folding underscores, whitespace, percent escapes, and a `User:` prefix while preserving case, because MediaWiki capitalizes only the first letter and casefolding would let a token issued to a different account satisfy the assertion.

Email subscriptions activate on subscribe rather than on a confirmation click, matching the talk channel: OAuth establishes the subscriber, the CentralAuth check establishes the account, and `emailuser` only relays to an address its owner already confirmed on-wiki, so a second opt-in verified a strict subset of what those establish while making every subscription depend on a live outbound send that returned 502 when it failed. `send_confirmation()`/`confirmation_url()` are removed; `POST /v1/digests/subscriptions/confirm/` remains and remains idempotent so signed links already in inboxes do not start 404ing. The clone that produces that peak is now bounded too: `repository_scan` clones with `--depth 1 --filter=blob:limit=<MAX_FILE_BYTES> --no-checkout`, enumerates with `git ls-tree -r -z` (no `-l`), and reads the selected blobs through `git cat-file --batch` under `GIT_NO_LAZY_FETCH=1`. It had reached 28 minutes against the 30-minute ceiling and the next run was killed just short of finishing; because the kill is SIGKILL the guard's EXIT trap never ran, so the run left its lock behind and recorded no failure, and the consecutive-failure alarm stayed silent — a pass that outgrows its timeout failed quietly and repeatedly rather than loudly once. An hour of headroom is free on a weekly job, where sampling or dropping phases would trade a bounded schedule cost for an unbounded correctness one in the pass that exists to be the global backstop. That job's premise that a skipped run costs nothing holds only against the per-minute drain, whose next attempt is sixty seconds away. It fails against the weekly full pass, which holds the same lock for 30-60 minutes — longer than the gap between two hourly runs — so the job is skipped on every attempt for the pass's duration rather than once; five consecutive skips were observed on 2026-08-17 while the guard still read `failure_streak=0`, because contention returns `EXIT_OK` by design and reports nothing. `job_runner.run_job` now forwards a `lock_wait_seconds` argument into the `timeout_seconds` that `db.advisory_lock` already accepted, defaulting to the existing skip-on-contact behaviour so every other caller is unchanged; only `--reconverge` passes it, at 120s. Waiting introduces no concurrency — the waiter still runs alone — so the deadlock history that made the lock shared is unaffected, and the wait stays under half the job's declared 600s timeout because waiting past a timeout is a SIGKILL, which is strictly worse than the skip it replaces: the same failure mode the weekly pass's timeout increase above addresses. Production JavaScript is concatenated at build time: tools/bundle_modules.py merges the module graph topologically into one shared scope, emitting an entry bundle, one chunk for modules more than one lazy route needs, and a chunk per remaining route, which takes the landing page from 39 module requests (122 KB) to 1 (94 KB gzipped). Measured in-cluster beforehand, a static module reported `Server-Timing: app;dur=1.9` against roughly 276 ms of wall clock per sequential request. Measured again from inside the pod, every asset returned in 5-11 ms and `cpu.stat` showed 109 of 484 periods throttled, so the cost is a fixed per-request overhead outside the pod rather than application work, bandwidth, or the 500m CPU cap; it does not shrink with the response, and request count was the only lever. An earlier note here attributed it to that cap, which the in-pod measurement does not support — the conclusion it justified, and the measured improvement, are unchanged. The build fails rather than guessing on a duplicate top-level name within a bundle, an import cycle, syntax with no single-scope equivalent, or an emitted import resolving nowhere; Worker modules stay on disk as separate realms with their `new URL()` rewritten root-absolute. The deploy's post-restart readiness probes now assert the response Content-Type is JavaScript, because app.py answers any unknown path with index.html and a 200 so cold client-side routes resolve, which had silently kept the previous per-module `curl -f` checks passing against assets the build no longer produced. The SPA shell is served from its build-time gzip twin as well. `/` carries an empty request path, so it never reached the branch that prefers a `.gz` and was the last asset still compressed per request — and it is also every cold deep link, which matches no file and is served the shell by that same line. Compressing in the request path clears `direct_passthrough` and buffers the whole body through memory instead of streaming it off disk, which measured 899 ms against 483 ms for the same 8.2 KB document in production, at 5-7 ms of server time either way. Trimming the document was measured and rejected: between 5,368 and 8,334 gzipped bytes there is no difference, and the only step down is below ~4,100, which would mean dropping the inlined critical CSS that first paint depends on.
