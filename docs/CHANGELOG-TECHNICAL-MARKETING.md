# Technical and Marketing Notes

- `catalog_projection.refresh_candidates` recognises three staleness triggers: a `projection_version` mismatch, `STATUS_ERROR`, and an analysis report newer than `refreshed_at`. A wiki census writes none of the three. `jobs.yaml` documents the contract in its own comment — producer jobs refresh changed tools immediately — and `canonical_tools.upsert_records` honours it, but neither `userscript_toolinfo.synchronize` nor `gadget_toolinfo.synchronize` ever did, which left 41,826 canonical rows in production newer than the projection rows reporting on them. Both `_write` functions already computed the answer and threw it away: they compare `row.record == record` to increment an `unchanged` counter. They now return those names, and `synchronize` hands them to `catalog_projection.refresh_tool_names` once the session has committed. `fetched_at` could not have served as the trigger — it is assigned unconditionally on every pass, so comparing it against `refreshed_at` would have re-projected the whole catalogue every hour rather than the rows that moved.
- `PROJECTION_SOURCE_BY_ROW` mapped `wiki_gadget` and nothing else, so every row synthesized from a user-space page fell through to the `SOURCE_CANONICAL` default and was published as `official_toolhub` at confidence 100 — outranking the 95 that `wikimedia_user_script` carries and every source that had actually read the page. The effect was legible in the coverage report as `human=10880`, exactly the gadget count, with all 37,863 user scripts counted in the toolinfo bucket instead. The mapping now carries one entry per wiki row source, and the comment above it names the omission itself as the failure mode instead of leaving it to be rediscovered. `PROJECTION_VERSION` moves to 5 so every row carrying the wrong source rebuilds; at `CATALOG_PROJECTION_LIMIT=20000` per hourly sweep the 57,385-row catalogue clears in about three passes.
- Worth naming rather than glossing: the gadget lane already had a test asserting exactly this contract, `test_the_projection_says_a_wiki_declared_this_not_toolhub`, and the user-script lane had no projection test at all — which is how an identical defect survived in the twin module while its sibling was covered. Four tests close that gap: the user-script equivalent of the gadget assertion, the licence reaching the projection from the census alone, a gadget reaching the projection with no `refresh_candidates()` sweep at all, and a pass that changed nothing asking for no rebuild. The last is the cost guard rather than a behaviour check; without it the new notification could quietly grow into a full rebuild every hour and nothing would fail.
- One residual gap, measured rather than fixed: 9,223 user scripts and 517 gadgets still carry no licence because their catalogue entry carries no creation date. The date does propagate — `userscript_projection.py` copies `UserScriptPage.created_at_wiki` onto the directory entry — and 478,155 of 478,530 pages are dated, so this is the previous release's licence work not yet having swept all 1,028 wikis rather than a fault in the path. It should close on its own as the census comes round. The honest thing is to re-measure in a day rather than build something for it now.
- Two repairs that continuous integration asked for rather than the catalogue. A newly published advisory against `browserslist` (GHSA-c83g-rgw3-j3cx: unbounded memory growth with no cache eviction, and a crash or prototype write reached through untrusted custom stats) had been failing `npm audit --audit-level=moderate` on every branch since it landed, which is why main sat red at `30ab5116` for a reason unrelated to anything that release shipped. The package is transitive and build-only, reached through `eslint-plugin-unicorn` and the Stryker toolchain, so the lockfile-only bump to 4.28.8 clears the finding without touching a runtime path. The checked-in Aethyme graph index is regenerated for the five files this release edits; `tools/aethyme_graph.py check` grades it by rebuilding and diffing rather than trusting a marker, so a stale index fails the branch even when every test passes.
- `catalog_facets.mark_dirty` read the facet dirty marker with `session.get` and inserted when it saw none, which is a read-then-insert under MySQL's default REPEATABLE READ. InnoDB fixes a transaction's consistent-read snapshot at its first read; for a 20,000-tool projection batch that is minutes before the marker is written at the end. Any of the other three callers — the hourly `catalog-projection` job, `userscript_toolinfo`, `gadget_toolinfo` — committing the marker in that window stayed invisible to the snapshot, so the INSERT hit the primary key and the `SQLAlchemyError` handler in `_refresh_batch` rolled the whole batch into `STATUS_ERROR` with exponential backoff. It fired twice during the `1e782c81` deploy and once more during the manual drain, which is how it was caught: a single bookkeeping row was discarding 20,000 computed projections. The marker is now stamped with an UPDATE, whose rowcount is the existence test, because writes read the latest committed row rather than the snapshot; a genuine miss inserts inside a SAVEPOINT that falls back to the same UPDATE. The caller's rows are flushed before that SAVEPOINT opens, so rolling it back can only ever undo the marker, never the batch — `begin_nested`'s autoflush behaviour has moved across SQLAlchemy versions, and the explicit flush is what removes that ambiguity. The regression test makes `Session.get` lie about the marker the way the snapshot did, and fails against the previous implementation with the production error verbatim.
