# Technical Release Notes

- Kubernetes delivers SIGTERM to PID 1 and nothing else. The Toolforge jobs framework composes every command as `/bin/sh -c -- 'exec 1>>NAME.out; exec 2>>NAME.err; <command>'`, so that wrapper shell owned PID 1 and `job_guard.sh` ran beneath it -- observed as PID 7 inside a live pod. A shell with no trap installed, waiting on a foreground child, neither handles the signal nor forwards it, so the guard was never asked to stop and was killed cold when the 15s grace period expired, leaking its lock every time.
- The previous release fixed the guard's own foreground-signal deferral, and that fix was correct but one level too low: nothing had asked whether anything above the guard swallowed the signal first. Prefixing each command with `exec` is the whole remedy -- the guard replaces the wrapper instead of forking under it, which puts it at PID 1. Verified on the platform with a throwaway one-shot job whose `ps` output read `PID 1 /bin/sh .../job_guard.sh`, not in a test that models the wrapper.
- `tests/tools/test_job_command_signals.py` reproduces the real wrapper string and signals only the wrapper, asserting the lock file is gone afterward. Dropping the `exec` prefix makes it fail with `the stopped run orphaned its lock`. A companion test rejects any command using shell syntax -- `&&`, pipes, redirects, `$(...)` -- that `exec` would break, so the prefix cannot be silently invalidated by a future edit.
- `people-identity-reconcile` declared `timeout: 900` while its finished runs landed at 879-889s, and the 15:43 and 16:43 runs on 2026-08-22 were killed at the deadline. A killed run writes neither a summary nor a run record, so it is indistinguishable from a slow one -- the job's own history is precisely where the evidence should have been. The timeout is now 1800 with `--stale-after` at 3600.
- Both numbers moved in one edit because `tests/proxy/test_workers.py` enforces `stale-after == 2 x timeout`: below the job's own timeout the guard would reclaim a lock from a live run. 1800 is twice today's cost rather than slightly above it, since the remote batch is bounded by its label limit but the local scan grows with the catalog -- 24,785 people and 27,506 evidence rows on the last completed run. It still fits inside the hourly schedule, so two runs cannot overlap.
- `people_reconcile.py` now reports `phaseSeconds`, splitting each sweep into its remote and local halves through a context manager that records the duration in a `finally` block, so a run that raises still reports the phase it died in. One total for a bounded batch followed by an unbounded scan cannot say which half needs the budget; more time is the wrong answer twice running if the local half is what grew.
- `canonical_tools.upsert_records` queued every fetched name for people reconciliation regardless of whether the stored record moved. A recovery snapshot re-reads the whole catalog, finds it unchanged, and queued 4,501 tools with nothing to do -- pinning a 25-rows-per-minute lane at its ceiling for about three hours, with generations 44 through 49 each staging 4,501 records and retiring none. The comparison now covers the whole record rather than the fields reconciliation reads today, so a future consumer of another field cannot be starved by the check.
