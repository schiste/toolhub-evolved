# Technical and Marketing Notes

- `userscript_coverage.snapshot()` took the `userscript-coverage-refresh` advisory lock before it read the stored roster. `refresh()` holds that same lock for its entire rebuild, roughly 25 seconds, so every reader during a census run burned the full two-second `GET_LOCK` timeout and was then handed the copy it had all along. The read is now lock-free; the lock is taken only on the paths that rebuild, where the row is re-read under it in case the holder just stored one.
- `api_cache.invalidate_graph()` deleted the shared graph row. `graph_payload.payload` is built to serve a stale copy instantly and refresh in the background — but that needs a copy to exist, and `graph_enrichment` invalidates on every facet change. Every such change therefore put the next visitor on a cold synchronous build. Invalidation now ends the row's fresh window via a new `_expire_where` beside `_delete_where`: deleting an upstream copy is free because the next request refetches it, deleting a derived one destroys the only copy there is.
- Measured in-cluster before the change: `/v1/graph/` 3788ms cold app time against 15ms warm, `/v1/userscripts/wikis/` 198ms cold against 19ms warm. Both cold paths were reachable by ordinary traffic, and both endpoints are fetched before their page renders, so this is time-to-first-content rather than background cost.
- The 1205 lock waits across ten jobs — 66 on `maintainer-backfill`, 41 on `repository-analysis`, 11 on `authorship-backfill` — traced to one holder, not ten bugs. The hourly `people-attribution-reconverge` deletes up to 500 `tool_summary_cache` rows in a single transaction; under REPEATABLE-READ a DELETE takes next-key locks over the gap it empties, blocking the continuous scan's INSERTs into that table for the length of the batch.
- Retries could not have helped and had not: `maintainer_backfill.record` is already wrapped in `run_with_lock_retry`, whose three attempts add about 0.6s of waiting, against a server lock-wait timeout of 50 seconds. The fix is where the commits fall. `reconverge_in_chunks` walks the same backlog and the same rolling cursor in committed chunks of 25 — each chunk was already an independently correct pass, so a chunk boundary is a place the job could have stopped anyway.
- `tool_summaries.refresh` now absorbs a per-tool lock loss instead of ending the batch. `_refresh_worker` stamps `last_error` on every name it was given, so one 1205 on the third tool both dropped the remaining builds untried and labelled them with an error they never hit. Only transient lock errors are absorbed; anything else still stops the batch, because it is not evidence about one tool alone.
- The census duplicate-key crash reported alongside these was already fixed in `015d10e5` and shipped: the savepoint retry is present, the commit is an ancestor of the deployed head, and the live job reports `failed=0`. No change was needed.
- Validation: 3,223 proxy tests pass, 25 skipped. New coverage on a chunked pass matching a single-transaction one, a chunk boundary surviving a later failure, a tool losing a lock race without dropping its queue, an invalidated graph still serving while it rebuilds, and a stored roster served without touching the lock. The two cache guards were mutation-checked — restoring the delete, and removing the lock-free path, each fail their test. ruff check/format and cspell clean.
