# Technical Release Notes

- `catalog_sync.recent_page` and `catalog_sync.listing_page` read the same paginated upstream API, and only one of them validated it. `listing_page` parses `count` and rejects a payload without a usable one; `recent_page` returned `bool(payload.get("next"))` and never looked at `count` at all. So an absent `next` -- the shape a degraded response takes -- was accepted as proof that the entire feed had ended.
- Reaching the end of the feed without meeting the saved cursor is what raises `RecentCursorLostError`, and `run()` answers that by re-walking the whole catalog through a recovery snapshot. The logs name the culprit precisely: of the three raise sites, `disappeared before it could be reconciled` has fired 20 times and the 200-page depth guard, which the surrounding comment was written to defend, has fired zero. The failure that never happened was guarded; the one that kept happening was not.
- Each recovery staged 4,501 records and enqueued every one of them for people reconciliation through the unconditional `enqueue_tool_names` call in `canonical_tools.py`. That lane drains 25 rows a minute by design, its batch deliberately halved after 50 held row locks for ~212s and deadlocked the source audit against the maintainer backfill. One recovery therefore pins the lane at its ceiling for about three hours, and 863 of 1,000 consecutive runs claimed a full batch. Generations 44 through 48 were five consecutive recoveries, each reporting `retired=0`.
- `recent_page` now believes an absent `next` only when `count` agrees the page is last, and otherwise raises `RecentFeedTruncatedError`. The feed is roughly 1,217 pages deep by its own count, so a shallow page claiming to be final is refutable from the same payload that made the claim. The check is sound because this feed only grows: a page with events still behind it cannot be the last one.
- The new error is a sibling of `RecentCursorLostError`, not a subclass, because `run()` dispatches on type alone -- so it falls through to the generic handler, the run fails, `recent_latest_marker` is left untouched, and the next scheduled run retries. Making it a subclass would silently restore the old behavior with nothing at the raise site to show it, which is why one test asserts the non-subclass relationship directly rather than trusting review to notice.
- Tests were checked against the failure rather than only against themselves: removing the count check makes `test_recent_page_rejects_a_last_page_its_own_count_contradicts` fail and restoring it makes the case pass again. The fixtures use the payload shape from a live read of `/api/recent/` taken while diagnosing, not one invented to match the code under test.
