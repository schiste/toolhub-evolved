# Technical and Marketing Notes

- The first `people-identity-reconcile` pass after the previous release deployed, 10:43Z on 2026-08-29, exited 1 at 205s of its 1500s timeout: `(1205, 'Lock wait timeout exceeded')` on `UPDATE person_identifiers`. With `innodb_lock_wait_timeout` at 50s the wait began around 10:44:46Z; of the scheduled jobs only `catalog-sync` and `repository-analysis` overlapped that instant and neither writes `person_identifiers`, so the counterparty was most likely the webservice rather than another job.
- Same failure family as the `person_reconciliation_conflicts` collision fixed in the last release, one table over — `_stamp_identifier_if_changed` already carried a note saying so. But the three observed aborts name three different row ids and three different `source` values, so that guard is firing correctly and these are real writes: deferring the write, which fixed the previous table, does not apply here.
- `job_runner.run_job` gains `retry_on_lock_timeout`. It is a number of seconds rather than a flag because the retry has to fit inside the job's own deadline: exit 1 sends mail, whereas a retry that overruns the timeout is a SIGKILL, and a kill is one of the three original ways a job dies saying nothing at all. Past the budget the database's own error is re-raised unchanged.
- Repeating the run is safe for the same reason `retry_on_disconnect` already was: by the time error 1205 surfaces the transaction has been rolled back, and every mode here re-decides its writes from present evidence, so the second attempt reaches the state the first would have.
- `people_reconcile.py` maps each mode to the Toolforge job that runs it and reads the budget from `job_catalog.load()` — half the timeout `jobs.yaml` declares, so 750s for `--identities-only`, 300s for `--reconverge`, 150s for `--queue`, 1800s for the full pass. Modes nothing schedules get 0: a ceiling invented in the entrypoint is how a retry ends up running past a timeout it never knew about.
- Exposure this does not remove: `wikimedia_user_reconciliation.synchronize` runs inside `run()`'s single transaction, so `person_identifiers` row locks are held until the whole pass commits — 1468s on the 07:43Z run. Narrowing that window is the structural follow-up, deliberately not bundled here.
- Validation: 107 tests across `test_job_runner.py`, `test_people_reconcile.py` and `test_lock_retry.py`, six of them new, covering the retried abort, the abort too late to retry, the opt-in default, a non-lock error, and each scheduled mode's budget pinned against `jobs.yaml` rather than restated in the test. Six broker gates, `pytest-proxy` in 246s.
