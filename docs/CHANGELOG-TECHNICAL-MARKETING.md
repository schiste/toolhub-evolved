# Technical Release Notes

- The repository scanner pointed git at whatever URL a tool record carried, and a record names where a _human_ should look. Gerrit browse URLs (`/g/`, `/r/admin/repos/`, `/r/plugins/gitiles/`) answered 403; GitHub `/tree/` and `/blob/` deep links answered "not found"; GitLab `/-/tree/` branch views redirected. `source_hosts.project_ref()` had resolved all of these correctly the whole time -- the enrichment lane queries the same URLs successfully -- so the scanner was not missing a capability, it was not using one. `clone_url(ref)` now builds the anonymous git URL from that resolved identity, and both `repository_head()` and the clone go through `git_target()`. Measured against every failing URL in production: 61 of 164 now resolve.
- Verdicts that need no request are reached without one. A record naming a known forge but no project on it -- `github.com/your-project`, the bare `gerrit.wikimedia.org/r`, a record whose URL is a forge domain and nothing more -- was cloned once an hour for the same "remote: Not Found" every time. `names_no_project()` settles those 12 rows up front, keyed to the record's own URL so an upstream edit is what reopens them rather than a timer. Hosts `source_hosts` declines to place on purpose, including the `*.github.com` and `*.gitlab.com` subdomains, are still cloned exactly as before.
- `_backoff` flattened at 24 hours, so a repository that is gone was asked about daily, forever. Production had settled at 199 failing rows with 195 of them pinned at the attempt cap, which is why the backlog lane reported 84-99% errors across four separate process lifetimes: it was spending its budget re-confirming URLs it had already failed on eight times. The curve now keeps doubling to a 30-day ceiling, turning 199 checks a day into roughly seven. Attempts one through four are unchanged and any success resets to zero, so a repository having a bad week is still retried within hours. A long interval rather than a terminal verdict, because a private project can be opened and a deleted one restored, and neither event edits the record.
- Gerrit's admin view percent-encodes the project's own slashes, so `mediawiki/extensions/GWToolset` arrived spelled `mediawiki%2Fextensions%2FGWToolset` and was encoded a _second_ time on the way to the API. `_gerrit_path` now decodes the one prefix that encodes. This was wrong in the enrichment lane too, not only in the scanner.
- `MAX_FILE_BYTES` is a cheap proxy for "vendored bundle, not source" in a checkout with hundreds of other files to read. A wiki tool is frequently a single page with no vendoring at all, so the same 256 KiB cap emptied the file list and the tool reached the analyzer as "files must be a non-empty list of {path, content}". fr.wikipedia's LiveRC, 700 KiB in one page, failed every scan that way; 11 of 1647 gadget source pages across the eight catalogued wikis sit over the old cap. `MAX_WIKI_FILE_BYTES` raises it to 1 MiB for wiki sources only, keyed on the `wiki_page` argument that only `_acquire_wiki` sets, so the wider ceiling cannot be asked for by a caller.
- These failures were invisible because `_save_failure` writes `status="error"` and prints nothing: the job never failed, never emailed, and the only trace was a counter in a JSON log line. The remaining 89 rows are genuinely unreachable -- 41 empty `toolforge-repos` placeholders, 48 deleted repositories confirmed 404 by hand -- and are now checked monthly rather than daily.
