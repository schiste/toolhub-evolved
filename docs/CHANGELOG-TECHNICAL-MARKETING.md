# Technical and Marketing Notes

- A job process was budgeted two connections, on the reasoning that a unit of work holds an advisory lock and a session at the same time. `run_job` holds more. When a caller queues for its lock it takes an _intent_ lock for the whole run alongside the real one, both entered on one `ExitStack`, so `people_reconcile` runs a session underneath two held locks and needs three. Its pool topped out at two: `QueuePool limit of size 1 overflow 1 reached, connection timed out, timeout 10.00`, at 15:21:20 on 2026-09-02, and `phabricator-realname-sync` the same way at 15:31:21. Both were introduced by the connection-budget work earlier that day, which is the honest shape of it -- the account stopped running out and two jobs started running out instead. Neither reached the guard's three-failure breaker.
- `CONNECTIONS_PER_LOCKING_UNIT` is three, and `run_job` declares whether it locks, because `run_job` is the code that takes the lock and the only place that can say so without every entrypoint repeating it. `projection_refresh` declares it as well, since its phases take advisory locks without going through `run_job`. Three is the measured width rather than a derived one: `people_reconcile`'s third connection is traceable, but `phabricator-realname-sync` does not queue for its lock and the path that spends its third has not been identified. Three is what covers the two runs that failed, the source comment says so, and it should be read that way.
- `CONCURRENT_JOB_PROCESSES` drops from the measured five to a planned four. Counting a locking job honestly, five leaves the account at 21 of a 20-connection grant, so this is the assumption that gives way rather than the arithmetic -- and it is now the weakest number in the file, declared where it can be seen rather than discovered again in production. Demand is 17 of 20 with two held back, against 19 before.
- `/v1/coverage/` returned one 500 in the same window and is deliberately not addressed here. It is already served from a cached snapshot that the deploy prewarms; the failure took 10,423ms, which is `POOL_TIMEOUT_SECONDS` plus overhead, so it waited for a connection and never got one rather than running a slow query. Caching it again would change nothing. The pressure is the webservice's two connections per worker against four threads, and the honest options there -- fewer threads, a smaller frontend fan-out, or a larger grant -- want the actual checkout depth measured first rather than a fourth guessed number.
- Validation: 3,606 proxy tests pass with 25 skipped, `ruff check`, `ruff format` and cspell clean, and the graph index was regenerated with the pinned 0.4.2 pair. Three existing tests failed before they were updated, one of them the `projection_refresh` drift guard added in the previous release, which matched a call string this change extends -- it fired exactly as intended, on its author.
