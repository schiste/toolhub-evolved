# Technical and Marketing Notes

- `people-identity-reconcile` (`43 * * * *`, 1500s timeout) failed three ways at once. Its own logs: 14 `(1205, 'Lock wait timeout exceeded')`, 20 consecutive `job-guard: reclaiming ... abandoned ~3600s ago`, and 8 consecutive `{"locked": true}` skips. Successful passes report `phaseSeconds` of `local` 1281.2 / 749.7 / 10.6 plus `remote` ~130 — so a full pass holds a shared lock for roughly 23 of its 25 available minutes.
- The fatal statement was `UPDATE person_reconciliation_conflicts SET run_id, last_seen_at WHERE id = 2700`, raised as a result of Query-invoked autoflush. `person_reconciliation_conflicts` is written both by `people_reconcile` outside `SOURCE_WRITER_LOCK` and by `source_attestations` under it, both inside multi-minute transactions, so a collision waits the full 50s `innodb_lock_wait_timeout` and takes the run with it.
- That write is cosmetic. `last_seen_at` has exactly two readers, both in the moderation queue — `v1_moderation.py:175` displays it, `:195` orders by it — and `CONFLICT_REFRESH_AFTER` means it is rewritten at most every six hours on a conflict whose contents have not moved. A conflict that genuinely changed is still written by the pass that decided it; only the unchanged ones are deferred.
- `refresh_conflicts_seen(ids, run_id=...)` applies them after the caller has committed, in a transaction of its own via `db.run_with_lock_retry`. Ids are sorted so two jobs refreshing overlapping conflicts take the rows in the same order and queue rather than deadlock. It forgives a lock — `is_transient_lock_error`, errnos 1205 and 1213 — and returns `{"requested": n, "refreshed": 0}`; anything else still raises, because swallowing a genuinely broken statement is the failure mode this whole line of work exists to remove. A deferred refresh past the caller's commit was chosen over a nested transaction, which on a second connection inside an open transaction can self-deadlock.
- `MySQL GET_LOCK` is not a queue: it hands the lock to whoever asks at the instant it frees. All four `people-*` modes contend for one `people-reconcile` lock, and the `* * * * *` drain (`lock_wait_seconds` 0, holding 6-11s) re-asks sixty times for every one time the hourly job asks and waits out its `HOURLY_LOCK_WAIT_SECONDS = 120`. Waiting bought nothing, which is what eight consecutive skips look like.
- `job_runner` now announces a wait. A waiter takes an intent lock — `<lock>:waiting` — for the length of the wait and holds it for the whole run; a mode that will not wait yields one of its own minutes when it sees one set. Held for the run, not released on acquisition, because a second waiter would otherwise queue on the main lock and end identically, and early release is the only variant that can leave the flag set with nobody behind it. Only the zero-wait mode yields, by the same reasoning that set its wait to zero. The announcement cannot extend the caller's wait: the remaining budget is what is left of it.
- `resolve_remote_batches` opens a short session, closes it, then does pure network — Wikimedia round trips paced by `REGISTRY_MIN_INTERVAL_SECONDS`. `run_job(before_lock=...)` lets `--identities-only` resolve its batch before taking the lock, cutting ~130s off the hold. Opt-in per caller, not a scaffold phase: the other modes resolve labels their own rebuild phase has just discovered. The trade-off is stated in the code — a run that prefetches and then loses the lock has spent that budget for nothing, acceptable because the batch is bounded and the prefetch doubles as time for the lock to free.
- Fourth silent-failure route, after the three in the previous release: `_run_once` returned `EXIT_OK` on a lock miss, so `/workers` recorded a successful run that never happened. It now returns `EXIT_SKIPPED` with the holder named (`heldBy`, `queuedBehind`, `yieldedTo`). Validation: 94 tests across `test_people_reconcile.py` and `test_job_runner.py`, including one asserting a refresh that can never succeed is not swallowed; all seven broker gates green, `pytest-proxy` 207s.
