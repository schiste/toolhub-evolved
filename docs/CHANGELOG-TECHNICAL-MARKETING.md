# Technical and Marketing Notes

- `catalog_coverage.snapshot` and `catalog_statistics.snapshot` opened an advisory lock and a session in one `with` block and returned the stored payload from inside it. `advisory_lock` holds a connection for the whole block, so serving a cached snapshot cost two — exactly `POOL_SIZE_PER_WORKER + POOL_OVERFLOW_PER_WORKER`. One `/v1/coverage/` request starved its own worker and the next waited out `pool_timeout` and returned 500: 10,423ms on 2026-09-02, which is `POOL_TIMEOUT_SECONDS`, not a slow query. The lock is now taken only on the rebuild path, with a re-read after acquiring it, and the stampede protection is unchanged where it matters — the loser of the race still serves stale, and a missing snapshot still takes the lock before building.
- Those tests assert the structure rather than the resource, and the first version of them did not. Counting concurrent connections passed with the defect in place, because `advisory_lock` returns without a connection on any dialect but MariaDB, so under SQLite the second connection does not exist. This is the second time in two days that SQLite has hidden a production cost: a no-op `UPDATE` is nearly free there too. The rule that keeps holding is to assert the shape the code takes, not the resource it spends.
- The 100% coverage ratchet then caught a genuinely untested path. Splitting one `with` into two made "acquired the lock, lost the race, serve stale" a distinct branch that nothing exercised — the exact property the lock exists for. Moving code between blocks is behaviour-preserving but reachability-changing, and coverage is what notices.
- `audit:js` failed a required check three times this morning while npm's `audits/quick` endpoint returned 503, for 7m52s, 13m29s and 7m15s of retries. `npm ci` in the same job reported `found 0 vulnerabilities` from its own install-time audit, so the dependency tree was never in question and nothing in the repository could have made the check pass. It had already blocked the same branch once before, for an advisory published mid-review. `npm audit` exits 1 both for findings and for failing to ask, and the check treated those alike.
- `tools/audit-js.mjs` reads the report instead of the exit code: any vulnerability at moderate or above still fails, and an endpoint error or unreadable output says loudly that the tree was NOT audited and exits zero. The two outcomes are different facts — a vulnerability is a fact about the code, an outage is a fact about npm, and blocking on the second buys no safety because the advisory set moves independently of the diff. Six unit tests cover the decision, and the behaviour was verified end to end against a stub emitting npm's own `{ error: 'Service Unavailable' }` payload taken from the failing run.
- Its entrypoint guard uses `pathToFileURL` rather than a `file://` template. The template never matches a checkout whose path contains a space, so `main()` never ran and the script exited zero having audited nothing — the exact silent pass the file exists to prevent, and invisible to unit tests that import the decision function directly.
- Validation: 3,717 proxy and tools tests, 1,393 vitest tests, coverage at 100.00%, `ruff`, `eslint` and cspell clean over 306 files, graph index regenerated with the pinned 0.4.2 pair.
