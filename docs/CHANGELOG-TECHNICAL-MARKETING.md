# Technical and Marketing Notes

- `modified_date` was the one catalog field no wiki lane ever filled. It is what `catalog_modified_at()` indexes as `modified_at_sort`, what the card and tool-page payloads carry, and what the frontend's "recently updated" sort orders on -- so every gadget and user script sorted as though it had never been updated at all. Both lanes now publish it, and the value is the current revision's `rev_timestamp`, not `page_touched`: `page_touched` also moves on a transclusion change or a null edit, and a catalog publishing it would report tools as updated on days nothing was edited.
- One indexed replica query per wiki dates that wiki's whole corpus, joined `revision r ON r.rev_id = p.page_latest` rather than aggregated as `MAX(rev_timestamp) GROUP BY page_id`. `page_latest` is the current revision id, so it is one primary-key lookup per page instead of a scan of the page's history -- the creation queries have to aggregate only because there is no `page_first`. Same best-effort contract as the creation dates: no `replica.my.cnf`, an unreachable replica, or a wiki `meta_p` does not name is zero rows written and no exception, and wikis that did not answer are omitted from the result rather than reported as 0 so the log distinguishes "nothing moved" from "no replica".
- The backfill and the recurring check are the same code, run unconditionally on every census tick -- `gadget-edit-dates` daily, `userscript-edit-dates` hourly, over fr, meta and en. This is not belt-and-braces: a gadget's definition page does not change when the code it points at is rewritten, so the inventory pass can honestly report a gadget unchanged on the very run its source moved; and the sweep skips pages whose `page_latest` it already holds, so the pages it can date are exactly the ones already dated. Dating only what a census touched would leave both lanes permanently stale.
- Writes are forward-only and never sideways: a stamp is written only when it is non-empty and strictly greater than the column. Backwards would mean history was rewritten under us, which a lagging replica looks identical to; sideways matters because assigning a column the value it already holds still writes the row, and an hourly job rewriting tens of thousands of rows to change nothing holds locks against everything else touching the table for no result -- the same fault as the no-op timestamp writes that were aborting deploys earlier this month.
- A user-script directory entry carries the original page's own last edit, not the newest across the pages folded onto it: an entry stands for one script, and a near-copy somebody edited last night says nothing about whether the script moved. Deleted pages are still dated, keeping the last edit they ever had rather than freezing at whatever the final sweep happened to see.
- `break: 100` in `stryker.conf.json` was never a threshold; it was a constant, and set at 100 it failed all nine shards on every run on record. It is replaced by a per-shard `floor` seeded from run 32862303176 -- the tree it guards, because a score is a ratio and other sessions' honest work landing between two runs dilutes it in a way indistinguishable from a test getting weaker. `organisms-qv` floors at 75 rather than the 100 it reported, because its RuntimeErrors never enter the denominator; that floor is a worst-case bound, not a measurement.
- Eighteen files matched the config's `mutate` glob and no shard's `--mutate`, so nothing ever mutated them while the score implied otherwise -- four of the largest views among them. `tests/unit/mutation-shards.test.mjs` now fails if a mutated file is claimed by no shard or by two. The 5741-line `core` shard, killed at the 60-minute ceiling on every run on record, splits four ways. Four tests that read the Stryker sandbox as if it were the source tree -- and so aborted their whole shard during the dry run -- now escape it for exactly the assertions that cannot hold there.
- Verification: 4 new suites and 4 extended ones, 361 proxy tests passing, including the census-job tests that pin the edit-date pass between the inventory and the catalog on every run and assert a wiki with no replica is still catalogued. Fake-replica tests cover the newest-of-several-files rule, an older answer never moving a stamp backwards, a row already holding the answer not being rewritten, a deleted page still dated, and one wiki's outage not hiding another's. On the mutation side: the aborting shard dry-runs rc=0 three times out of three against three failures before, and 1326 unit tests pass.
