# Technical and Marketing Notes

- `routeSkeleton()` no longer returns null. Routes with a purpose-built shape already rendered one; everything else fell back to a spinner beside `router.loadingToolhubData`, so the fallback path was the one that produced the written sentence. It now returns a generic page skeleton — head, prose lines, card grid — for any unmatched path, which makes the return type total and deletes the branch that rendered text. The key was renamed to `router.loadingPage` because it no longer describes loading the local catalog specifically, and `SPINNER_DELAY` is untouched at 250ms: a view that resolves inside it still swaps straight from the old page to the new one without rendering a loading state at all.
- One `loadingRegion()` owns the accessibility contract for every wait. The visible label was a defensible decision executed wrongly: the shapes carry `aria-hidden`, so the live region has nothing to announce without a text label, and the label was therefore kept on screen. The correct answer was `.visually-hidden`, not deletion. The helper emits `role="status" aria-live="polite" aria-atomic="true"`, a hidden label, and an `aria-hidden` body, and the route placeholder, the authenticated-account placeholder, and the three in-view states all go through it, so the pattern cannot drift apart between them.
- Cold boot needed the skeleton CSS inlined. Stylesheets load through `rel="preload" data-deferred-style` and are activated by `main.js`, so anything painted before JavaScript runs has only the inline critical block to work with — a boot skeleton built from `molecules.css` would have rendered as unstyled text on a blank page. The critical block in `index.html` gained the skeleton primitives, the animation, `.visually-hidden`, the reduced-motion guard, and `--color-skeleton-base`/`--color-skeleton-sheen` for both themes; `frontend-startup.test.mjs` now asserts the boot placeholder is a skeleton and that each of those pieces is present in the critical CSS, since dropping any one of them fails only in the pre-hydration frame that no other test renders.
- The in-view states reuse each page's own layout classes. The workers grid, the statistics report head and ledger, and the graph canvas skeletons are built from `workers-page__inner`, `statistics-report`, `statistics-ledger` and the real card and section classes rather than parallel skeleton layout, so the placeholder inherits the grid the content lands in and nothing reflows on arrival. Two places needed explicit rules because a placeholder has no text to size it: `.workers-card__ident` is a flex item that collapses to zero width without `flex: 1 1 auto`, and the map skeleton's height cannot be derived from a canvas that is `min-height: 260px` until the graph renders at 560. That duplicated 560 is pinned by a test that reads it out of `organisms.css` and out of the `forceGraph()` call and asserts the two agree, and the dead spinner rules — `.route-loading--auth`, the visible-label rule, `.statistics-page .spinner` — were removed with the markup that used them.
- The user-script watch seeds its cursor and follows the feed. Two faults compounded. `sweep()` never wrote `changes_cursor`, so a completed pass left it empty, and `changes_params("")` sends no `rcstart` — with `rcdir=newer` the API then starts at the oldest row `recentchanges` still retains, about thirty days, so a wiki fresh from a full sweep began watching a month in the past. Separately a watch read exactly one window per run, and `WATCH_LIMIT` is capped at 500 by the API for a client without `apihighlimits` — roughly ninety minutes of en.wikipedia's User namespace against an hourly schedule, so the backlog drained at half an hour per hour and would have taken two months. Wikis that edit slowly climbed out of the same month-back start within a day, which is why it presented as an en-only fault. The cursor is now stamped when a pass begins rather than when it ends, because a bounded sweep spans runs and a page read in the first run can be edited before the last one finishes; and one run now follows the API's own `continue` object for up to 48 windows, about three days of en.wikipedia, so an outage is repaid on the next run instead of over weeks. Following the continuation rather than re-asking with `rcstart` is what makes that safe at the boundary: a window can end mid-second, and re-asking at that second re-reads part of it. A wiki already current still costs one request, the cursor advances only over windows that were fully ingested so a run cut short by maxlag re-asks only the window that failed, and a run that exhausts its budget reports `behind=1` — in every other count that is indistinguishable from a quiet hour.
