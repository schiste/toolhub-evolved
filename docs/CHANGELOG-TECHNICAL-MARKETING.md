# Technical and Marketing Notes

- The previous release moved exactly one tool, and measuring why produced both changes here. Its rule — top up any keyword list below two — was correct code against an empty set: where inference succeeded the tool had no upstream keywords at all, so the pre-existing empty-field fill had already given it five or more, and where a list was short the inference had been rejected. Mixed-source keyword lists in production: 0. The reachable population was the intersection of "list is short" and "a usable reading exists", which was one tool.
- The 3,942 rejections turned out not to be a defect. 79% are the model returning a well-formed `{"description": null, "keywords": []}` — the abstention the prompt asks for. Rejected pages are not short (median body 1,210 chars, p90 50,435) and were not truncated (86% sent whole). They are pages that are not tools, so no prompt change should recover them: `morebits.js` is rejected on 103 of 103 pages because it is Twinkle's library, copied.
- `ToolInference` grows a `lane` column, which its own docstring had anticipated ("a second lane would need its own join column"). `page_id` now holds the row id in whichever table the lane owns — `user_script_pages` or `wiki_gadgets` — so it may only ever be read together with `lane`; a test asserts a cross-lane read yields nothing rather than silently attributing one lane's answer to the other's row.
- The gadget lane asks for keywords and nothing else, and `FIELDS_BY_LANE` makes that structural rather than a property of the prompt. A gadget already has a maintainer's description in `MediaWiki:Gadget-<name>`; a model that volunteers a second one has it dropped exactly as an unasked-for `license` is. This is the same reasoning that excluded gadgets originally, applied one field at a time instead of to the whole lane.
- Deliberately one ask per gadget, not one per gadget name. Keying on the name would have been 3.2x cheaper — `hotcat` is declared on 434 wikis — but it would publish one wiki's reading onto 433 others and tie every row to a fingerprint computed from text that is not theirs, so a local edit could never return the gadget to the window. Re-inference keys on `description_fingerprint`, which collapses whitespace so a reflowed message is not mistaken for a rewritten one. `_interleave` then alternates the two lanes rather than concatenating them: about 8,000 user scripts are still unasked and `pending` returns up to `BATCH`, so a gadget queued behind them would wait weeks, and the gadget lane is the one with 10,882 records at zero keywords.
- `tool_shape.classify` is deterministic first and uses the model's verdict only where no name can decide. `monobook.js` is the case that forces this: 15% of them hold a real script, against 100% for `morebits.js`, so a skin file is called configuration only when the lane also declined it. Every doubt resolves toward "this is a tool", because a wrong reclassification hides a real maintainer's checklist while a missed one shows a checklist nobody needed.
- `_shapes_by_tool` starts from `ToolInference.tool_name`, which is the only place a catalogue name and a user-script page are stored together — `tool_name` slugs in Python and `user_script_pages` keeps no copy of it, so a query starting from the page could not be narrowed to a batch and would read all 166,399 rows per 500 tools. The cost is that a page nobody has asked about is not classified and keeps its checklist, which is the safe direction.
- Validation: 3,649 proxy tests and 1,404 vitest tests, with `inference_enrichment`, `catalog_projection` and `tool_shape` all at 100% statement and branch coverage; `tsc --checkJs`, eslint, prettier, cspell and `ruff check proxy` clean. The gadget fixtures are three real Lift Wing replies captured on 2026-09-04 for descriptions in Russian, Acehnese and French — the point being that a reply composed here could not have shown whether the English instruction works. Rollout is gradual: about 10,000 asks at roughly half of each hourly wave.
