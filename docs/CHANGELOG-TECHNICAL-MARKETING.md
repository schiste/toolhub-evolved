# Technical Release Notes

- `wiki_source()` typed any `MediaWiki:Gadget-*` title as `KIND_GADGET`, but that title is a naming convention and registration is the predicate: the Gadgets extension serves a gadget because a line in `MediaWiki:Gadgets-definition` names its files. The resolver performs no I/O and so cannot know, and it now returns `KIND_GADGET_PAGE`. Only `registered_gadget(source, definition)` returns `KIND_GADGET`, and it settles the kind and the page set in one pass because one definition line answers both.
- The scanner already had the answer and dropped it. `_wiki_revisions` fetches the definition to learn a gadget's page set and comments that an unregistered page "is a leftover or a work in progress rather than a gadget", then returned only the revisions. It now returns the resolved source too; `_Source` carries it through acquisition, and `scan_tool` passes it as `analyze_source_files(..., wiki_page=...)`, which records it in the report under `wikiPage` beside the suggestion it produced.
- The policy is an absent mapping entry rather than a branch: `KIND_GADGET_PAGE` has no term in `WIKI_KIND_TOOL_TYPE`, so a page that is unregistered and a page that was never checked -- which know exactly as much as each other -- both yield no `tool_type`. Neither falls through to the technology heuristics either, since a wiki page of unestablished kind is not a Flask application; without that guard the fix would have moved the bug one namespace along and started answering "web app" for the `mw.Api` every gadget page contains. `gadget_toolinfo` already typed from the inventory built out of `gadget_entries`, so this brings the analyzer into line with the lane that was right.
- Eleven tests, at all three levels: a definition promotes a page and a missing or empty one does not, a user script is never put through the registry, the resolved kind reaches the analyzer over a real scan of both a registered and a retired gadget, and an analysis that fetched no definition claims no gadget -- which is the `POST /v1/source-analysis/` path, taking files from a request and now declining to assert a registration it cannot check. The wiki fixture stubs the analyzer, so the scan tests record the keyword arguments it was handed rather than asserting on a field the stub invented.
- Also in this release: the icon cache held 80 rows in `status="error"`, every one a `commons.wikimedia.org/wiki/File:...` URL reporting `unsupported icon content type: text/html`, with `attempts` as high as 31. That is not bad data -- toolinfo specifies `icon` as a Commons file-description page, so the records were right and the fetcher had simply never resolved a description page to the file it describes. `_wiki_file_url` rewrites `/wiki/File:X` to `/wiki/Special:FilePath/X` on the host the record already named, so it resolves a URL rather than widening reach. Rasters are requested with `?width=512` because a tool's icon is frequently a screenshot; vectors are asked for whole, except that `_fetch_icon` catches the `ValueError` raised by `PUBLIC_IMAGE`'s 512 KiB body cap and retries once for a scaled copy, one sampled Commons SVG being 437 KB. The rewrite sits in `_icon_source` so that `refresh_candidates`, which re-queues on `asset.source_url != url`, picks all 80 rows up on the next hourly run instead of waiting out their backoff.
