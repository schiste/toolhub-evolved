# Technical Release Notes

- The React rule in `TECH_RULES` was `\bReact\b` under `re.IGNORECASE`, evaluated against every file the analyzer reads rather than only code. That matched the English word in prose and, because lockfiles are read too, the substring in `node_modules/react` -- so any checkout that had ever installed React was catalogued as a React tool. It is now `\bReact\.[A-Za-z_]|\bfrom ["']react["']|\brequire\s*\(\s*["']react["']`, case-sensitive, and gated through `TECH_RULE_SUFFIXES` to JavaScript files so a fenced `import React` in a README stays documentation.
- Tightening the pattern alone would have converted a false positive into a false negative, because the end-to-end fixture's React detection came only from `"dependencies":{"react":"latest"}`. `TECHNOLOGY_PACKAGES` now promotes a declared package to the technology it names, at `DECLARED_TECHNOLOGY_CONFIDENCE = 0.8` -- below every source-observed rule, since declaring a dependency is evidence of intent to use rather than of a use. The declared/resolved split is judged on `source_classes`, not `category`: `development` is emitted by both `Pipfile` and `Pipfile.lock`, so category cannot discriminate, and a lockfile row names every transitive package a build would fetch.
- `.jsx` appeared in none of `SOURCE_EXTENSIONS`, `FRONTEND_SOURCE_EXTENSIONS`, `TECH_BY_EXTENSION` or the import-scan set, so `is_supported_source_path` rejected it and `analyze_source_files` answered `no supported source files were provided`. `.mjs` and `.cjs` were listed in `BROWSER_SCRIPT_SUFFIXES` but were likewise unreadable, making those entries dead. All three lists are now one `JS_SOURCE_SUFFIXES`, since "may this file be read", "are its imports npm imports" and "is `mw.Api(` here a call" are the same question, and keeping three copies is what let them disagree. The new suffixes join the `frontend` source class at weight 0.95 rather than falling through to `unknown` at 0.55, because `source_reading_rank` orders the file budget by class weight -- a readable `.jsx` at 0.55 would still lose its slot to the repository's docs.
- Version capture splits two claims that were previously one. `Finding.version_specs` holds each constraint as the manifest wrote it; `Finding.versions` holds the subset pinning a single release, normalized. `payload()` emits `version` only when `len(self.versions) == 1`, so two manifests disagreeing yield specs and no answer. Constraints naming no version (`*`, git URLs, workspace locators) are dropped rather than stored, and the yarn/pnpm scanner became a pending-locator state machine because those formats write the resolved version on the line below the locator -- a locator followed by another locator emits `None` instead of borrowing its neighbour's version. A manifest pinning a runtime (`engines.node`, `requires-python`, `require.php`, the `go` directive) creates the technology finding; a package version only annotates one the source already proved.
- `v1_common.source_technology_summary` carries the result onto the public payload, capped at `MAX_PUBLIC_TECHNOLOGIES = 20` to match the analyzer's own patch cap, omitting any technology with no declared version. The catalog field is untouched: `technology_used` is a toolinfo vocabulary term, so `Flask 3.0.2` cannot go in it. `tool.js` joins the two at display time, matching names case-insensitively because upstream catalog entries and the analyzer disagree on capitalization often enough that an exact match would drop the version for `python` but keep it for `Python`.
- `source_repository_summary` whitelisted eleven of the thirteen keys a stored `repositoryContext.repository` can hold, silently dropping `archived` and `dirty`. Both are scored -- archived is terminal for maintenance status, a dirty checkout downgrades the analysis -- so the payload could not explain a verdict it was already reporting. `False` is kept rather than collapsed to absent, matching the scanner's own `_host_facts` boundary: a host that says "not archived" has told us something, a host with no such field has not. A test asserts the emitted key set against `REPOSITORY_CONTEXT_REPOSITORY_KEYS` so an upstream addition cannot go unread here.
- The contradiction warning counted distinct values in a projection field. A projection row is one value, not one source's whole answer, so a set-valued field carries a row per member -- `isa` alone reports eight technologies and eleven wikis, each its own row and each effective. The rule is now "a source offered evidence that was retained, judged valid, and still left out", with case-insensitive comparison and list normalisation so `python` and `Python` are one claim. `mwext-codemirror` is the population that must still warn: repository analysis says `web app` against an effective type of `other`.
- Validation across the seven commits: 2658 proxy tests and 1278 frontend tests pass, with 26 new tests. Every new guard was mutation-tested and each mutation kills at least one test -- among them reinstating the distinct-value contradiction rule, loosening the React pattern back to `\bReact\b`, dropping each of `.cjs`/`.jsx`/`.mjs` from the suffix set, narrowing the frontend class again, letting a yarn entry borrow the next entry's version, and accepting a disagreeing pin as the version. `ruff check`, `ruff format --check`, cspell, eslint, tsc, banana and i18n:check are clean.
