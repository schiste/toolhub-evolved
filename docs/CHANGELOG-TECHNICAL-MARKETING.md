# Technical and Marketing Notes

- `_upsert_relationship_evidence` selected its row and then assigned all eleven columns unconditionally. Every assignment marks the instance dirty, so SQLAlchemy issued an `UPDATE` and InnoDB took a row lock to store the values already present. `tool_relationship_evidence` is written by six jobs and rewritten by `people-reconcile-incremental` every minute, where confirming an unchanged observation is overwhelmingly the common case. MySQL error 1205 — lock wait timeout exceeded — had failed runs 179 times across ten jobs by 2026-09-03. An earlier version of this note called those failed runs, which was wrong and overstated the impact: `maintainer_backfill` wraps its per-tool write in `db.run_with_lock_retry`, so its 72 are retries that then succeeded, and its guard streak never left zero. The accurate claim is 179 logged lock-wait events of which an unknown fraction were absorbed; `people-identity-reconcile` and `toolinfo-source-index` are the two that genuinely failed, and only the second lacked a retry.
- This is the third occurrence of one defect in one file, and the previous two named it. `_stamp_person_if_changed` fixed it for `people`; `_stamp_identifier_if_changed` fixed it for `person_identifiers` and describes itself as "the defect `_stamp_person_if_changed` describes, one table over and missed when that one was fixed". This is one table over again, and it is the table the lock waits were on.
- `checked_at` is included in the suppression rather than stamped regardless, which changes its meaning to when the observation last changed rather than when it was last confirmed. Two `ORDER BY` clauses in `people_index` rank supporting evidence by it, so an unchanged row now sorts below a recently changed one, and `checkedAt` in the relationship payload may lag. Nothing filters or expires on it — `expires_at` carries that — so the cost is ordering and display, paid deliberately: stamping it unconditionally is exactly what made a no-op write unavoidable, so keeping it would have kept the lock and left the defect standing.
- The test counts emitted `UPDATE` statements rather than comparing values, because the values were always correct and it was the writes that were wasted. A value-based test passes throughout the defect, which is the likeliest reason it survived two previous fixes of the same bug. It was checked against the unconditional write restored, and caught it as `assert 1 == 0`.
- What this does not establish: SQLite makes a no-op `UPDATE` nearly free and takes no meaningful lock, so the suite proves the statement is gone and only production can show the contention falling. It also removes one writer's unnecessary writes, not the other five's necessary ones. `maintainer_backfill`'s transaction shape is unexamined despite carrying the most timeouts, and neither it nor `toolinfo_sources` opts into `run_job`'s existing `retry_on_lock_timeout`. The measure of success is MySQL error 1205 ceasing to accumulate over hours, not a green deploy.
- Validation: 3,609 proxy tests pass with 25 skipped, `ruff check`, `ruff format` and cspell clean, graph index regenerated with the pinned 0.4.2 pair.
