# Technical Release Notes

- Adds a durable digest domain over captured official tool-creation events, immutable edition/tool snapshots, publication state, channel subscriptions, and a restart-safe delivery outbox. UTC day, ISO-week, and calendar-month boundaries are deterministic, generation is idempotent, missed closed periods recover automatically, empty periods are suppressed, and idempotent MariaDB migration widens complete rendered bodies to `MEDIUMTEXT`. Public catalog reads now resolve locally through `/v1/catalog/*`; complete Toolhub snapshots stage by generation and publish in one transaction, failed imports preserve the prior generation, the obsolete request-time HTTP client and revalidation worker are removed, and scheduled workers are the only anonymous Toolhub network readers. Canonical ingestion derives compact card JSON and indexed UTC modification timestamps, background jobs atomically publish global facet aggregates, filtered facets use a covering index and independent endpoint, redundant canonical revalidation is removed, and card rendering no longer waits for facet or summary enrichment. Projection version 4 lifts Toolhub `tasks` and `audiences` annotations without treating API-owned annotations as top-level fields; one shared facet vocabulary preserves legacy `technology` compatibility while exposing canonical `detected_technology`, `declared_technology`, and `ui_language` names across REST and MCP. MCP search uses the atomic local replica, GET `/mcp` returns a structured 405 pointing to a lazy-loaded in-app guide with client-specific configurations, and every new message includes translator documentation. Release notes remain collapsed when no deployment record exists.
- Integrates LiftWing's public OpenAI-compatible `llm-qwen36-27b` chat-completions endpoint with strict Wikimedia host/path/model validation, contact-bearing user-agent headers, bounded timeouts and citation-only payloads, period-wide candidate sampling for busy weekly and monthly editions, Qwen reasoning-tag removal, schema validation, unique supplied-title normalization to canonical tool ids, exact full-field or whitespace-normalized verbatim excerpt evidence checks, and an audited deterministic fallback with sanitized failure details. Daily requests and responses cover every supplied tool exactly once; weekly and monthly responses select exactly `min(total, 5)` tools; omissions, duplicates, ambiguous or invented identifiers, paraphrases, and trivial fragments remain fail-closed. A database-free live preflight exercises production facts through inference, validation, and rendering before deployment.
- Publishes canonical edition pages and the archive tree on Meta through a bearer-authenticated Wikimedia Action API client that restricts destinations, verifies the configured service-account identity, bounds responses, refreshes CSRF tokens, and classifies permanent recipient failures. The same client appends talk-page sections and calls `emailuser` without adding SMTP infrastructure. Configuration-sourced outbound header values are now validated next to the configuration that supplies them rather than inside `requests`: `proxy/backend/http_headers.py` folds interior whitespace runs in descriptive values, because a Toolforge envvar wrapped across lines unambiguously means its single-line form, and refuses whitespace or control characters in credentials, because folding a token would transmit something other than what was configured. Error messages name the variable and never quote its value, which is what makes them safe to return; `WikimediaClient` construction failure is a 500 naming the envvar rather than a 502 that would misdirect an operator upstream, and `LIFTWING_USER_AGENT` is validated inside `generate_editorial()`'s fallback guard so a malformed value degrades to deterministic copy with a recorded diagnostic instead of stopping publication. `WikimediaClient` additionally redacts its access token from transport-exception text, since `requests.InvalidHeader` quotes the offending header value verbatim and that string reaches both the API response body and the stored per-subscription `last_error`. All three 502 branches of `POST /v1/digests/subscriptions/` now log; the module previously imported no logger. The service-account assertion in `csrf_token()` compares MediaWiki spellings rather than raw strings: `WIKIMEDIA_ACCOUNT_NAME=NellieBly_Bot` and the Action API's `NellieBly Bot` name one account, and raw equality made the writer fail to recognize itself and route every write into the permanent `unexpected-account` branch. `canonical_username()` is split out of `normalized_username()` for this, folding underscores, whitespace, percent escapes, and a `User:` prefix while preserving case, because MediaWiki capitalizes only the first letter and casefolding would let a token issued to a different account satisfy the assertion.
- Exposes public edition APIs, local blog routes, per-cadence RSS feeds, authenticated subscription/status APIs, lifetime unsubscribe links, stable Wikimedia identity checks, bounded delivery retries, and per-subscription suspension without cross-channel impact. Email subscriptions activate on subscribe rather than on a confirmation click, matching the talk channel: OAuth establishes the subscriber, the CentralAuth check establishes the account, and `emailuser` only relays to an address its owner already confirmed on-wiki, so a second opt-in verified a strict subset of what those establish while making every subscription depend on a live outbound send that returned 502 when it failed. `send_confirmation()`/`confirmation_url()` are removed; `POST /v1/digests/subscriptions/confirm/` remains and remains idempotent so signed links already in inboxes do not start 404ing. A migration activates rows stranded awaiting a confirmation nothing will send, matching only `confirmed_at IS NULL` so a deliberately stopped subscription is not revived by a later deployment, and stamping `confirmed_at` at migration time rather than backdating it, because delivery gates on `confirmed_at <= edition.period_end` and a backdated stamp would make an already-published edition eligible.
- Adds a compact responsive archive and human-scale edition layout, summary-only archive payloads, accessible subscription controls, localized English strings with translator documentation, immutable permalink and feed discovery metadata, and regression coverage for routes, rendering, confirmation, delivery, RSS, outbound guards, identity trust, and UTC period behavior. Subscription views surface backend failure detail rather than the transport status line: `public_html/views/digests.js` drops a local helper that returned `Error.message` and discarded the JSON body, and calls the shared `backendErrorMessage()` at both the subscribe-submit and confirm/unsubscribe catch sites. `BackendError.message` carries only `Backend ${status} ${path}` by construction, so the three distinct 502 branches of `POST /v1/digests/subscriptions/` — unverifiable CentralAuth identity, `WikimediaAPIError` during the cross-wiki account check, and confirmation-email send failure — were previously indistinguishable in the interface. `backendErrorMessage()` prefers `body.details.message`, then `body.error`, and falls back to `Error.message`, so network failures keep their existing text; it is used in preference to `backendErrorExplanation()` because that helper maps every 502 to a "no official change was published" sentence, which is false for the email-send branch where the subscription row is committed before the 502 is returned.
- Schedules publication at 06:15 UTC, delivery every five minutes, and an hourly audit. Job locks reclaim at twice each timeout; audit failures cover missing configuration, recent Qwen fallback, overdue generation, Meta/archive failure, exhausted delivery, and stale validated or queued work. Due-period scanning is bounded by `DIGEST_BACKFILL_DAYS` (90) and one coordinator pass generates at most `DEFAULT_MAX_EDITIONS_PER_RUN` editions, reporting the surplus as `remaining`; without both bounds the sequential generate-then-publish pass spent its whole timeout walking the catalog back to 2021 and never reached publication. `digest_publish.py --max-editions` raises the cap for a supervised operator backfill without changing the scheduled budget. Push delivery is gated on `published_at - period_end` against `DIGEST_MAX_PUBLICATION_LATENESS_DAYS` (14) — a property of the edition rather than of the wall clock, so it is stable on re-evaluation and identical on every replica — and subscription eligibility compares `confirmed_at` to `period_end` rather than to publication time, which only stood in for it while publication was prompt. An idempotent migration retires previously generated, never-published, never-delivered editions whose period closed before the horizon to a terminal `out_of_scope` status; emptiness rather than nullity is the marker, since the `meta_page_*` columns default to `""`. `repository-analysis` now declares `mem: 2Gi`, because the Toolforge default of 512Mi cannot hold a `git clone` resolving a large pack: the measured cgroup peak over one 100-tool batch was 1.264Gi against a 150Mi steady state, so neither `kubectl top` nor the analyzer's own 64Mi checkout and 2Mi input caps observe it — that cap rejects an oversized working tree only after the clone that produced it. The resulting kill was self-perpetuating rather than intermittent: SIGKILL leaves `job_guard.sh` unable to record an outcome and leaves the candidate's `repository_analysis_state` row untouched, so ordering re-selected the same repository first on every following run. The job therefore made no progress between 2026-08-13 and 2026-08-17 while its guard state still read `failure_streak=0 disabled=0 last_exit=0`, which is why nothing alerted. The clone that produces that peak is now bounded too: `repository_scan` clones with `--depth 1 --filter=blob:limit=<MAX_FILE_BYTES> --no-checkout`, enumerates with `git ls-tree -r -z` (no `-l`), and reads the selected blobs through `git cat-file --batch` under `GIT_NO_LAZY_FETCH=1`. The filter alone is inert, because reading an absent blob makes Git refetch from the promisor remote and that refetch is not object-granular — asking pallets/flask for one 233-byte blob pulled the whole 3.3M blob set, and `ls-tree -l` triggers it as well, since printing a size requires holding the object. Only the three together hold: no checkout means nothing reads a blob to materialize a working tree, and `GIT_NO_LAZY_FETCH` turns a would-be refetch into a `missing` reply, which is the same verdict the analyzer already reaches for anything over `MAX_FILE_BYTES`. Selecting by tree mode replaces deleting symlinks from disk, since a mode check cannot be raced and needs nothing materialized, and `MAX_FILES` now counts accepted files rather than selected candidates, topping up across chunks past rejected ones. Fetched bytes fall 3.7x on flask, 16.5x on requests, and 4.7x on pywikibot, each slightly faster, with byte-identical analyzer input; the retained `MAX_CHECKOUT_BYTES` gate still covers the residual case the per-blob filter cannot bound, a repository of very many small files. With the clone bounded, the hourly batch of 100 became the remaining limit, and it was one budget shared by two kinds of work with opposite economics: backlog entries are finite and each is a real clone and analysis, re-checks never end and are usually a single HEAD lookup that finds nothing moved. `repository-analysis` is now `continuous: true` with two independently paced lanes — backlog every 1s, re-check every 60s, both settable by environment variable — and each tick runs whichever lane is most overdue, so a saturated fast lane delays the slow one by at most one in-flight tool instead of starving it; interval means minimum spacing between starts, so a slow clone cannot make the loop run hot to catch up, and one catalog pass every 300s fills both queues rather than a table scan per item. `checked_at` is now stamped before the clone rather than after it, because `_scan_order` puts a never-checked row first: a pod killed mid-clone reselected the same repository on every restart, which a scheduled job survived until an operator noticed and a continuous one would not. `job_guard.sh` is deliberately absent — its `--stale-after` lock reclaim would fire against a live process that never exits, and its three-failure breaker would exit 0 forever, converting a crash loop into a silent no-op loop — so Kubernetes restart is the supervisor; but the guard was also the only writer of `JobRun` rows, so `backend/job_runs.py` is extracted and the loop publishes a 300s heartbeat that `job_catalog` and `/workers` judge silence against in place of a cron period. `mem` drops 2Gi to 1Gi, roughly six times the measured 159.7MiB peak.

Adds an anonymous Phabricator profile provider and a `phabricator_real_name` identifier namespace so Toolsadmin-style author labels — which carry the Phabricator `realName`, not the Developer account `cn` — can join to a person. The provider reads only the public `/p/<username>/` page over the shared bounded outbound path against a fixed `PHABRICATOR_BASE_URL`, refuses any handle outside `[A-Za-z0-9._-]{1,64}` before percent-encoding it into the path, treats 404, an unparseable header, and a redirect to another account alike as "no profile", and never turns a transport failure into a cached negative. An hourly `phabricator-realname-sync` job spends its request budget first on the Developer accounts that maintain a tool carrying a name-shaped unresolved author label, then continues a cursor walk over the remaining accounts; priority reads never move that cursor, the cursor advances only past accounts whose every stale handle was read so the SUL-name fallback is never silently dropped, and an outage stops the window on the account that failed. Reads are cached in `phabricator_profile_projection` with distinct 90-day profile and 365-day missing TTLs, and the whole cache is re-judged each sweep so policy changes take effect without refetching. Acceptance is deterministic and fail-closed: the name must come from a `developer_username` or `wikimedia_global_name` handle, exactly one account may publish it, no other person may already own it in a public handle namespace, and a name that only casefolds back to the handle is refused; disabled accounts stay eligible. The namespace is excluded from the public handle list so a sweep cannot read its own prior write as a conflict, corroboration still requires an independent verified same-tool edge from another source, and superseded names are retired idempotently. The Toolforge membership projection now reads tool memberships from the authoritative forward direction: every `(&(objectClass=groupOfNames)(cn=tools.*))` entry under `ou=servicegroups` is paged on the same connection as the account search, and the group DNs each account's `memberOf` list omits are restored before normalization. Wikimedia's reverse `memberOf` index is maintained by an overlay that never backfilled the tool groups created before it existed, so 981 of 6623 real memberships and 666 of 4374 tool groups were invisible — concentrated in the oldest estates, whose feeds therefore had no derivable controller and fell through to `service_registered` at confidence 0. Members that are not people, such as a tool's own service account under `ou=people,ou=servicegroups`, are skipped, and the per-account membership bound rises from 100 to 500 so the restored lists are not silently truncated at the busiest developer's 108 memberships. With those memberships restored, the `registered_source_toolforge_host` mapping was tightened: it had made every LDAP member of the project hosting a toolinfo feed a verified maintainer of every tool the feed lists, which conflates control of the feed with control of the tools inside it. The feed's host now only selects which tools to consider, and the maintainer edge is emitted only when the person also belongs to a project the tool's own `CanonicalToolCache` record is served from — an independent half the publisher does not author. `canonical_tools.runtime_host_project_names` resolves that record across every runtime host form Toolforge has used, `$PROJECT.toolforge.org`, the legacy `tools.wmflabs.org/$PROJECT` path, and `.wmflabs.org` / `.wmcloud.org` proxy subdomains, with the path hosts matched before the suffixes so `tools.wmflabs.org` is never read as a project named `tools`. Five candidate rules were measured against production first: requiring the feed's own project to match the tool's runtime host drops 316 of 414 edges and leaves 222 tools with no verified maintainer, because the uncorroborated set is dominated by multi-project owners publishing one feed for tools served from several projects rather than by spoofing. Requiring person-level membership in the serving project keeps 377 of 414 and leaves 19, and because it only filters the candidate set the previous rule already produced it can withhold an edge but never invent one. The `canonical_tool_name` mapping is exempt, since there the record already names its own project, and each surviving edge records the shared projects in its evidence payload. `corroborated_handle_person` now asks its two questions in the opposite order: it queries the corroborating same-tool evidence first to build a candidate set, then tests the label for a unique match among only those candidates' current handles, comparing on a `_handle_key` that keeps alphanumerics after NFKC folding. Scoping uniqueness to one tool's proven people is stricter about what counts as proof, not looser — the tie is broken by who demonstrably holds the tool rather than by whether the name is globally unowned, nothing is admitted that the same-tool edge did not already establish, and the cross-source rule still prevents self-confirmation on a rerun. The reversal is also what makes separator-insensitive comparison feasible, since handles are stored under the exact normalizer and a fuzzy key cannot be pushed into SQL, while reading one tool's handful of people back into Python is cheap. The global-scarcity test had let an unrelated person sharing a handle veto a match, and separator-exact equality kept `lokal-profil` from meeting `Lokal_Profil` and the Toolsadmin Phabricator real name `Bryan Davis` from meeting `BryanDavis` — that account alone carried 67 unresolved author labels whose same-tool corroboration was already sufficient. The publishability gate is unchanged; replaying the predicate against production resolves 193 of 2735 pending author observations across 26 labels with 0 ambiguous. One `tool_name`-indexed evidence query now runs per identity-less observation where the old path could short-circuit on a `normalized_value` lookup; the index and the few-row candidate set keep that inside reconcile rather than paying for a second squashed column. Stored unresolved attributions are now re-decided against evidence that arrived after they were first judged. Corroboration is the one attribution rule whose answer can change without its own observation changing, and nothing revisited it: an observation was judged at ingest and its verdict then fixed by whichever feed ran first, so a corroborating edge landing later changed nothing until that feed was re-ingested for that tool — for most rows the weekly full pass, which left 370 rows across 125 labels that the deployed rule already resolves sitting in the backlog on feed order alone, 59 of them one account's. `people_index.promote_unresolved_attribution` re-runs corroboration for one stored row, which is faithful because a row reaches that table only when it carried no identifier of its own, making its stored columns the whole observation and corroboration the only outcome that can change; the evidence upsert is shared with the ingest path so the two cannot record the same observation differently. `people_reconcile.reconverge_attributions` walks the backlog in bounded batches behind a rolling id cursor, filtered by a correlated `EXISTS` that mirrors the corroboration query's own candidate predicates exactly so no row the rule would promote is ever skipped, and the cursor wraps at the tail so a permanently unresolvable row cannot starve the rows behind it. It runs last among the evidence phases of an apply pass, and on its own hourly `people-attribution-reconverge` job sharing the `people-reconcile` advisory lock, since concurrent identity writers have deadlocked this table before and a skipped run costs nothing while the cursor persists. Convergence latency falls from a week to hours, and a widened rule now reaches existing rows instead of waiting for their feeds to come round. Verified Toolforge project aliases also admit a runtime host that collapses to the record's own name-derived project: upstream canonical names collapse hyphen runs, so the internationalised project `xn--9s9h` arrives as the record name `toolforge-xn-9s9h` and no derivation from the name can restore the lost character, leaving every punycode project's LDAP membership mapped under a name LDAP does not use. The host is not trusted to name the project — it is checked against the name that already does, so a record naming one project while linking to another project's launcher still fails — and `names_by_toolforge_project` now passes the record through so the LDAP index reaches both spellings.
