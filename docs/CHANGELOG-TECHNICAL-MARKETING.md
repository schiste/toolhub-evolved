# Technical and Marketing Notes

- The discriminator is the client's own error code, not a size estimate. `_read_batch` returned a bool; it now returns `READ_OK` / `READ_TOO_LARGE` / `READ_FAILED`, read off `error.code` against `ERROR_RESPONSE_TOO_LARGE` from `wikimedia_delivery`, and a single title refused for size increments a new `oversized` count instead of `unreadable`. `read_titles` returns a `Read` NamedTuple rather than a positional triple. The rejected alternative was a `rvprop=ids|size` pre-query: one extra request per fifty titles -- roughly 195 per full en.wikipedia sweep, roughly 1,152 a day in watch mode -- to avoid about ten, and it would have had to guess how much JSON escaping adds to a page's byte count, where guessing high drops a page the census could have read. The bot-maintained user list at the root of this is 1,975,719 bytes of source and 2,234,764 as a response against a 2 MiB `MAX_RESPONSE_BYTES`; the client measured that, so asking it is exact where inferring it is not.
- The memo is per run and lives in the caller. `read_titles` takes an optional `known_oversized: set[str]`, `ingest` threads it through, and `watch()` holds one set across all 48 of its windows -- which is the case that matters, because a run catching up over several days meets a daily-edited page in several of them. Known titles are moved out of the batching and asked for individually; they are still asked for, since a page can shrink and a memo that stopped asking could never find out. This also protects `SPLIT_BUDGET`: the five splits are budgeted per `read_titles` call over a 500-title chunk, so a handful of oversized pages in one chunk could previously exhaust it and cause whole batches of perfectly readable pages to be written off as unreadable.
- The field prints only when it is not zero, and `_read_halves` lost its degenerate base case. `oversized=N` follows the `collisions` convention in the census log line for the same reason and with a sharper edge, since this one has a standing cause and would otherwise read as an incident on every run of every wiki. `_read_halves` no longer needs `if len(batch) <= 1: return ([], len(batch))`, because the single-title verdict is now taken where the status is known; its callers guarantee two or more titles, so neither half is ever empty. Five tests cover the split, that a codeless failure stays `unreadable`, the solo re-ask, the cross-window memo, and the suppressed zero.
