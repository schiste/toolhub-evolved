# Technical and Marketing Notes

- The refactor was made falsifiable before it was made. `tests/proxy/fixtures/catalog_statistics_snapshot.json` records the entire `build_snapshot` payload for a fixture seeding every branch -- six tools, three people, five relationships with evidence, seven unresolved labels, three sources, two attestations -- and the test asserts equality against the whole document rather than a handful of keys. `UPDATE_GOLDEN_SNAPSHOT=1` rewrites it in place with tab indentation, so regeneration is a diff of numbers and never of whitespace. It earned its keep immediately: the streaming rewrite replaced a per-field `dict` with a `Counter`, which silently dropped `metadata` entries whose count was never incremented and lost `CORE_FIELDS` ordering. Nothing else in the suite noticed.
- `build_snapshot` accumulates instead of materializing. The old shape built a `records` dict of all 16,827 canonical tools -- ORM entities, decoded JSON columns and all -- and then ran list comprehensions over it; peak memory scaled with the catalog and the pod died at Toolforge's 512Mi default with exit 137, surfacing as a 503 on `/v1/statistics/`. Every query now selects columns rather than entities and streams through `_stream()` at `yield_per=500`, and `_year_histogram(list)` / `_recency_histogram(list, now)` became `_YearHistogram` / `_RecencyHistogram` accumulators taking one value at a time. `Person.id IN (...)` over the publishable set became an in-Python membership test against a set already in memory, removing one bind parameter per person. The `createdByYearBySource` split added alongside it keeps its meaning: the lane a row belongs to is a column on that row, so the two per-lane histograms accumulate in the same single pass rather than costing a second read of the catalog, and the fixture now seeds a wiki-sourced tool so both lanes are pinned.
- Freshness is now produced on a schedule instead of by whoever asks first. `SNAPSHOT_MAX_AGE` is fifteen minutes and the only writer was `projection-refresh` every six hours, so the common case was an expired document and a 12.7s inline rebuild inside a request. `proxy/statistics_refresh.py` runs `catalog_statistics.refresh()` on `*/10 * * * *`; `snapshot()` prefers a stale document over rebuilding, bounded by a new `SNAPSHOT_STALE_LIMIT` of six hours so a dead job cannot freeze the page forever. A test pins the schedule inside the window it promises -- `job_catalog.load()` interval must be non-zero and at most `SNAPSHOT_MAX_AGE` -- so the two constants cannot drift apart again.
- Job timing was chosen by the repository's own invariants, not by preference. `tools/job_guard.sh --stale-after` must equal twice the declared timeout, and a reclaim threshold must not land within `RECLAIM_MARGIN_SECONDS` (120) of a schedule tick; timeout 300 / stale-after 600 satisfied the first and failed the second by landing exactly on the ten-minute period. Timeout 240 / stale-after 480 puts first look at 600s with a margin of exactly 120. The job takes no `job_runner` lock of its own -- `refresh()` already serializes on the advisory lock the web workers respect, and a second lock only adds a way for the two to disagree.
- `proxy/service.template` raises the container limit to 1Gi. Four uWSGI workers idle around 261Mi of the 512Mi default, which left no room for one expensive read. `webservice` reads exactly one template from `~`, `~/www/python/src`, `~/www/js` or `~/public_html` and `sys.exit(1)`s on a second, and `find_service_template()` runs before the action is parsed, so a single copy under `proxy/` -- the target of the `~/www/python/src` symlink -- applies to `restart` as well as `start` with no change to `tools/deploy.sh`. 1Gi sits inside the namespace quota (3584Mi of 8Gi) and the LimitRange maximum of 6Gi. Tests assert exactly one template is tracked and that its `type` matches the webservice deploy starts.
