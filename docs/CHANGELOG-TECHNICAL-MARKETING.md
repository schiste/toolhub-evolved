# Technical and Marketing Notes

- `digest-audit` is an alarm wrapped in `tools/job_guard.sh`, which disables a job after `MAX_FAILURES = 3` consecutive non-zero exits and thereafter permits one trial run per `RETRY_AFTER`. An alarm exits non-zero when something _else_ is broken, so the breaker read a working alarm as a broken job and muted exactly the signal it was meant to protect: 16 failures from 08:00 on 2026-08-30, then one run roughly every two hours. `job_guard.sh` gained `--no-breaker`, set on `digest-audit` in `jobs.yaml`. The failure streak is still counted and still recorded; only the disable path is off. A flag rather than unwrapping the job, because unwrapping also discards the per-job overlap lock, the `--stale-after` abandoned-lock reclaim, the `TOOLHUB_JOB_SUMMARY_FILE` handoff and the `job_runs` row the per-worker pages chart. `job-watchdog` is unwrapped for the same alarm-role reason and the two are now cross-referenced from both sides.
- The alarm was independently wrong about when a period is late. `ToolActivityEvent.event_at` is the upstream creation time and is back-dated relative to `captured_at`, which is when `catalog-sync` ingested the row: the tool was created at 2026-08-30T22:01:21 and captured at 2026-08-31T06:30:15, fifteen minutes after `digest-publish` had run at 06:15 over a period that was still empty. `MAX_DUE_PERIOD_AGE` measured eight hours from `period.end` against a generator on a twenty-four hour cycle, which guarantees a false report for up to twenty-two hours. A new `digests.overdue_periods(grace=...)` ages each due period from whichever came later, the period closing or the earliest `captured_at` among its events, which is the first instant a run could have produced it; the threshold is now twenty-six hours, one full cycle. Both halves are needed. `captured_at` alone still flags a 06:30 arrival at 14:30 with no run due until the next morning, and a longer threshold alone still starts the clock before any run has seen the period.
- Generating more often was the rejected alternative: the 06:15 delay is the settling window that lets a day's late arrivals land before an immutable edition freezes that day's tools, so the fix belongs in the audit rather than in the schedule. The missing edition itself was produced by a one-off Toolforge run of the real guard-wrapped `digest-publish` command, reporting one created and one published with no fallback, and is live. Validation: 3,517 proxy and tools tests with 25 skipped, eight of them new. Four encode the incident timeline directly, asserting the period is not late at 09:00 the same morning, is late once the next scheduled run has passed, that a promptly captured period still ages from the period close so the alarm still fires, and that generating the edition clears it. Three cover `--no-breaker` in `job_guard.sh`, including that a permanently failing alarm still runs on its sixth consecutive failure and that the overlap lock and summary-file handoff survive the flag. One asserts that both the flag and `emails: onfailure` are present in the `digest-audit` block, so the alarm cannot be muted again by a later edit. One existing test grew an explicit `captured_at`; it had been relying on the wall clock. Broker gates on the merged tree pass: jscpd-python, pytest-tools, ruff-check, ruff-format, cspell, prettier and pytest-proxy.
