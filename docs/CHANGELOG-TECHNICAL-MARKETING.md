# Technical and Marketing Notes

- Catalog search put the whole query into one `LIKE '%...%'` against `search_text`, so a match had to contain the words contiguously and in order. Measured against production before the fix: `Lupin` and `popups` each returned results, `Lupin popups` returned none, as did `twinkle gadget` and `article previews hover`. `_search_text` joins name, title and description with newlines, so no query spanning two of those fields could match however it was spelled.
- `canonical_tools.search_terms` and `search_predicate` now split on whitespace and AND one escaped substring test per term, capped at `MAX_SEARCH_TERMS = 8`. Both call sites route through them: the bug was one line in two copies, and the second copy is the offline fallback for the first — so a failed catalog search fell back to a path with exactly the same defect.
- AND rather than the scored OR the MCP tool advertised, because no scorer exists: `search_payload` with no `ordering` falls through to sorting by tool name. An OR over 53,000 rows with nothing ranking it would answer "wikipedia bot" with a thousand alphabetical tools matching only "wikipedia". The `search_tools` description and the `prior-art-review` prompt were corrected to say each extra word narrows and that an empty result means no record contains all the words.
- Separately: three jobs died on every tick this month with no automatic signal — `crawler` breaker-tripped for ten days from 2026-08-03, `catalog-validation` OOMKilled for a day from 2026-08-25, `inference-enrichment` OOMKilled for sixteen hours from 2026-08-27. Toolforge mails on a non-zero exit and nothing else, and a job has three ways to die without one: SIGKILL, which skips `job_guard.sh`'s exit trap so no `job_runs` row is written; the guard's overlap skip; and the guard's breaker, the last two exiting 0 by design.
- Detection was never missing. `workers._status` has always classified every declared job against its own period — `LATE_PERIODS = 3`, `STALLED_PERIODS = 10` — and calls a stalled worker the state that "must be impossible to miss". Its only consumer was the `/workers` page, so the gap was that nothing polled it. `job-watchdog` is that poller: hourly, it exits `EXIT_SWEEP_FAILED` naming every worker that is stalled, failing, or late.
- It deliberately does not run under `job_guard.sh`. The guard disables a job after three consecutive non-zero exits, and this job exits non-zero exactly when something else is wrong, so a stall lasting three ticks would retire the only thing reporting it — the same shape as the crawler failure it exists to catch. A structural test asserts the `jobs.yaml` command contains no `job_guard.sh`.
- Two deliberate limits, both pinned by tests. `unknown` (never ran) is named in the report but never alarms, because it reads identically for a job deployed a minute ago and one broken since birth. And the watchdog records its own run as `EXIT_OK` even while alarming, so a verdict about other jobs cannot mark it permanently unhealthy or hide its own death behind somebody else's.
- Validation: 11 new search tests and 12 new watchdog tests. All seven broker gates green on both merged trees, `pytest-proxy` in 136s and 108s.
