# Technical and Marketing Notes

- `MediaWiki:Gadgets-definition` is now read as a manifest, rights and dependencies alike. The scan already located the line registering a gadget in order to learn which pages it consists of, then discarded the rest of it. `gadget_declaration()` returns the parsed entry with the line number and raw text it came from; the analyzer emits one `accessRights` finding per declared `rights=` value and routes each `dependencies=` module through `_put_dependency` in a `resourceloader` ecosystem, so a module naming an API client is read as one by the same rule that reads npm and PyPI clients. Across 487 measured entries, 235 declare dependencies naming 71 distinct modules. The page is classed `manifest` by title rather than through `MANIFEST_FILE_KINDS`, whose values select a dependency parser it must never reach.
- Declared rights dedupe with observed calls, and stay outside the write categories with a consumer of their own. The vocabulary maps each MediaWiki right onto the same value slug `ACTION_RIGHTS` uses, so a gadget that declares `rollback` and is also seen calling it produces one row carrying both pieces of evidence, and the declaration is scanned after the source files, so the category an observed call assigned survives — `_put` sets a category once, on first insertion. `rights=` states an audience gate, not an action, so every declared right is reported under `restricted` at confidence 0.9, just under an observed `action=` call's 0.94, leaving `writeActionsDetected` settled by code that was actually read. `restricted` used to be a category nothing consumed: a gadget gated on `rollback` with no rollback call fell through to permission-clarity's read-only branch and scored 90 — safer than a tool whose code was read. It now takes a 70 branch of its own, and the finding carries a badge in the UI so a declared gate does not render identically to an observed action.

- The vocabulary is measured, and now re-measured on a schedule the data enforces. The first reading of five definition pages found 69 of 488 entries declaring twenty-one distinct rights. Reading fifteen more — the es, ru, ja, it, pl, pt, zh, nl, sv, ar, fa and he Wikipedia editions, meta, en.wikisource and en.wiktionary, 1576 entries — found 36 of 189 declarations naming seventeen further rights, `protect` and `review` among them. Every report now carries `declaredRightCount` and `unknownDeclaredRightCount`, and `repository_scan` logs the rights it cannot describe, so the next nineteen-percent gap announces itself instead of decaying silently.
- Gadget reach travels on the `wikiPage` row, not as permissions. `gadgetDefault`, `gadgetHidden` and `gadgetScope` surface as one neutral permission-clarity signal contributing nothing to the score. Reading `default` alone overstates: of 85 `default` entries only 16 are unqualified, 44 carry `namespaces`/`actions`/`skins`/`rights`/`categories`/`contentModels` limits and 25 are also `hidden`. Keys are absent rather than false when no definition line was read, so "not measured" stays distinguishable from "declared opt-in".
- What the page makes the reader's browser do is now scored and read. `browserPermissions` was collected, listed, and ignored by every health dimension; it gets one of its own at weight 0.7, graded by `browser_permission_reach` — device, browser, or the page the code already runs on — with an extra penalty for an all-sites request. The assessment returns `None` for a tool that asks for nothing, so the dimension is `applicable: false` and no published grade moves. Separately, `.css` files counted against the file budget without being parsed; `@import` and `url()` references to third-party hosts now raise a privacy warning, chosen over the endpoints bucket so `STATIC_ASSET_RE`'s deliberate icon filter stays intact.
- Archived tools left the default search population. `catalog_read` selects `catalog_facets.default_population()` unless `include_archived` is set, and that parameter also forces real facet counting because the cached aggregate is built over the default population only. The page-size controls were also deduplicated into `public_html/lib/core/paging.js`: `PAGE_SIZE_OPTIONS` is Fibonacci 8..144 with `DEFAULT_PAGE_SIZE` 21, replacing the `[12, 24, 48]`/24 triple that search, authors and accounts each declared separately. 144 is the ceiling `MAX_PAGE_SIZE` and the `maximum=` arguments in `v1_accounts.py` and `v1_people.py` clamp to, and they clamp silently — an option above it would render pages the pager counts but the API never returns, so both ends move together or neither. There were two clamp layers, not one: `account_directory`, `community_search` and `people_index` clamped again at 100 after the HTTP parser, so all six now read `backend/paging.py:MAX_PAGE_SIZE`. The offline fallback was reading a wider population than the page it replaces: `canonical_tools.search()` selected straight from `CanonicalToolCache`, so a failed catalog request answered with archived rows. It now builds on `default_population()` unless `include_archived` is passed, which `cachedCanonicalTools` sends from the Status filter; fetching by `names` is unchanged. Shipping it needed a second fix: two deploys of this release died in the account-linking migration on MySQL error 1205 against `person_identifiers`, after `git pull` had already fast-forwarded the host and before `dist/` was rebuilt, so production kept serving the previous build. `_normalize_identifier_vocabulary` already deferred a held chunk, but the linking pass that follows it writes the same table through `link_user` and had no guard; the refusal also arrives out of the SELECT opening `ensure_person`'s next upsert, so it reads as `Query-invoked autoflush` rather than as the UPDATE that earned it. Linking now walks accounts in `BACKFILL_CHUNK` windows and leaves a held chunk to the next deploy, which is the contract the identifier pass already had.
- Feature-status artifacts were regenerated against what the analyzer does now. The source-analysis entry listed a bucket set two releases stale; automatic repository and on-wiki analysis, the worker behind the repository-analysis provenance label, had no entry at all.
- Reconfirming an unchanged `person_identifiers` row no longer restamps it. `_upsert_identifier` assigned `last_seen_at` and `updated_at` unconditionally, so a pass that changed nothing still emitted `UPDATE person_identifiers SET last_seen_at=..., updated_at=...` and took a row lock to store a value no query selects — `_restate_identifiers` in `migrate.py`, its only reader, tests it for NULL. `people-reconcile-incremental` rewrites this table every minute, so confirming an unchanged identifier is the common case, and it aborted the 2026-08-24 deploy twice inside `_backfill_people_identity` with `(1205, 'Lock wait timeout exceeded')` on row 14078, leaving the host pulled but still serving the previous build. `_stamp_identifier_if_changed` now gates both timestamps on `Session.is_modified(row, include_collections=False)`, mirroring `_stamp_person_if_changed`, which cured the identical defect on `people` on 2026-08-21 and was never carried across; a `created` flag stamps new rows, which report as unmodified while pending. The user-linking block of `_backfill_people_identity` remains one transaction over every user, unlike `_normalize_identifier_vocabulary`, which chunks and defers on 1205/1213 — a genuinely contended row can still abort a deploy there.
