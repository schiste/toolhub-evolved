# Technical Release Notes

- `job_guard.sh` wraps every scheduled job in a lock directory released by an EXIT trap, and that trap could never run at termination. A POSIX shell waiting on a _foreground_ command defers a trapped signal until the command finishes, so the platform's SIGTERM sat unhandled until SIGKILL arrived a grace period later. Every run stopped at its timeout therefore orphaned its lock, and the trap looked like it covered the case.
- `people-reconcile-incremental` shows the shape exactly: scheduled every minute, `timeout: 300`, `--stale-after 600`. A run killed at 300s left the lock, the next 300 ticks failed to take it and skipped, and the tick at +600 reclaimed it -- so the job's `.err` held nothing but `reclaiming ... lock abandoned 600s ago` on a ten-minute cycle. A skip exits 0, so `emails: onfailure` never fired and one killed run quietly retired the job for ten minutes at a time.
- The child now starts in the background with the guard waiting on it, which is the whole reason the signal becomes reachable. The handler stops the child, waits for it, then releases the lock -- in that order, because a lock released while the child is still writing lets the next tick start a second concurrent run, and concurrent reconcilers are what deadlocked the source audit and the maintainer backfill in the first place. The exit happens before the breaker state write, so a stop initiated by the platform is not counted as one of the three failures that disable a job.
- Age-based reclamation is unchanged and is now what it was written to be: the backstop for a run killed outright, with no chance to run any code. The twice-the-timeout `--stale-after` rule still holds and is still enforced by a test over every job in `jobs.yaml`. Three comments that presented it as the only recovery were corrected instead of left to teach the next reader that an abandoned lock is normal.
- Verified under `/usr/bin/dash` on Toolforge rather than only locally, because macOS `sh` is bash in POSIX mode and trap-and-wait semantics are precisely where the two shells could differ: lock released, exit 143, the child's own TERM handler observed to run, breaker state untouched, and exit codes 7 and 0 still propagated. Three new tests cover the released lock, the stopped child and the untouched breaker, and reverting each behavior in turn fails a different set of them.
- `tests/tools/test_check_changelog_freshness.py` built scratch repositories without scrubbing `GIT_DIR` and `GIT_INDEX_FILE`, which git exports to its hooks. Run from inside the pre-commit gate, its `git init`, `git add` and `git commit` calls landed on the repository being committed to: two commits nobody wrote, and `core.bare = true` in the shared config, which breaks every worktree at once. The fixture now drops the seven variables that name a repository and keeps the four that name an author.
